# The director

See the [project root AGENTS.md](../../../../AGENTS.md) for repository-wide policies.

The director keeps an org tree of agent teams, each with an IC and a Manager, and a team memory. It is code with fixed rules, not an agent. What follows is decided; keep to it when changing the module.

## Org tree and team memory

The director (`openhands-agent-server/openhands/agent_server/director/`, routes in `director_router.py` under `/api/director`) keeps an org tree of agent teams and a team memory in hidden git refs (`refs/agents/org`, `refs/agents/memory`) of the org's repository. That is the git repository of the workspace of the org's first conversation, wherever the server was started: `create_org` moves `DirectorService._repo_dir` there and writes it to `director.json` beside `Config.conversations_path`, which is read first on the next start. Until there is an org, the director looks in `Config.director_repo_path` (default `workspace_path`). A repository that has no org and is a git submodule stands for the nearest repository above it that has one (`DirectorService._load_from`), both at startup and when a first message arrives; `OrgSummary.repo_path` is the org's repository and `OrgSummary.directory` is where the server's own directory sits in it, which is where a message without a `path` is routed from. Tests that start an org through the app must point `conversations_path` at a temporary directory, or `director.json` leaks between them. `GitStore` never touches the working tree or the user's index: it builds trees in a throwaway `GIT_INDEX_FILE` and lands them with a compare-and-swap `git update-ref`, retrying when another writer wins. `OrgStore` owns the derived `child_ids`, `descendant_counts` and `escalation_count` and is the only emitter of org events; mutate the tree through it. A stream subscriber follows one focus node plus the nodes it has expanded (or the whole subtree with `full`), and gets the list of escalations that wait on the human, for the whole tree whatever its focus, whenever that list changes.

## Escalations

An escalation never goes straight to the human: it is held by the node above the one that raised it and moves only through `OrgStore.pass_up_escalation`, one node at a time with a reason, so `held_by` is `None` only after every node above has passed it up (the store rejects anything else). Keep it that way when adding ways to raise or route escalations. Escalations run in two lines: `Escalation.raised_by` is the role of the agent that raised it, and at each node it is that role's agent that is told and that may settle or pass it up with `resolve_escalation` (`pod_actions._hand_to`), so an IC's goes IC to IC and a Manager's Manager to Manager; the human's answer goes to the agent that raised it. The wire types are mirrored by hand in `clients/typescript/src/models/director.ts` (client-ahead of the pinned release); change both together. `DirectorService` loads nothing until first use, so `create_app` stays free of git calls.

## Agents are conversations

An org's agents are ordinary conversations: `POST /api/director/org` starts the root IC from the caller's `StartConversationRequest`, and every other agent is derived from an existing one with `ConversationService.start_child_conversation` (a Manager from its team's IC, a sub-team's IC from the IC above), so model configuration and secrets stay in the conversation store and never reach the org ref. The director reaches conversations only through `PodLauncher` (`director/pods.py`), which tests replace with a fake.

## Agents that run their own tools

An agent that runs its own tools (an `ACPAgent`: Claude Code, Codex) can be any agent of an org, the root IC included. It cannot be given the director's tools in-process and its tool calls never pass `guard_action`, so `DirectorService._adapter` changes it as its conversation starts (the `adapt_agent` hook of `start_conversation` and `start_child_conversation`): `mcp_config` gains the stdio MCP server `director/mcp_shim.py` (standard library only, run by its path), which lists the tools from `GET /api/director/tools` and passes each call to `POST /api/director/tools/{name}`, and `acp_command` is prefixed with `<git dir>/director-shells/<conversation id>.acp.sh` (`sandbox.command_script`), which starts the agent's whole process in the team's sandbox with the team's `git` first on `PATH`. Those two routes are mounted outside the session-key dependency: the caller is known only by `X-Director-Agent-Token`, an HMAC of its conversation id (`director/acp.py`) with a key kept in `director.json`, so it survives restarts and never reaches the org ref. They run the same `pod_actions` as the in-process tools (`director/tools/remote.py`); add a tool to `DIRECTOR_TOOLS` and to the role that may use it in `service.TOOLS_OF`, and both ways get it. A tool's free text is named `text` in every tool; name a new tool's the same. An agent is offered only its role's tools: `DirectorService._adapter` puts them in place of the ones a derived agent carries from the agent it was derived from (a Manager from its IC), and `GET /api/director/tools` lists them by the caller's role; `pod_actions._only` stays the check. What an agent always reads is kept short, so keep to it: `POD_PROTOCOL` holds what every IC needs from its first turn, `MANAGER_ROLE` the Manager's part, which only a Manager is given, and what concerns a rarer event is said in the message that brings it (`review_request`, `stall_notice`, `approved_notice` with `WITH_SUB_TEAMS`, the hand-over brief, `manager_check`). Put new guidance in the message of the event it is for, not in the protocol. The shim needs the server's own address: `director_server_url`, or else the base URL of the director's last request. Without bubblewrap nothing holds an ACP agent's process, so its IC always gets its own worktree and what it commits outside its directory is refused at merge-back; `OrgNode.boundary_enforcement` says which holds per team (`sandbox`, `checks`, `merge`), and an ACP Manager is then held by its prompt alone. A proposed sub-team may run on another agent with `model` in its `teams` block (`SplitChild.agent_profile`), a name from `DirectorSettings.allowed_profiles`; that team's IC is started from the stored profile with `PodLauncher.start_from_profile` as a child of the IC above, its Manager derived from it as always. The director's one-shot model calls (`summarize`, `ask`) are put to an ACP agent itself with `ask_agent`, since it has no model the server can call.

## Tools and effects

Agents act on the org through the tools in `director/tools/`, which run in-process: a tool resolves its caller with `OrgStore.find_by_conversation`, `director/pod_actions.py` checks the caller's role and node, and anything that touches a conversation (starting agents, sending messages, saving the tree) is queued with `DirectorService._enqueue(effect, lane)`. Effects of one lane run in order and lanes run side by side: a team's node id for its starts and messages, `review:<id>` and `headline:<id>` for its model calls, `org` for saves. An effect that must follow another has to share its lane. Keep it that way: tools run on agent threads and must not wait on a conversation, and nothing may call back into the store from a store listener. A start the server refuses because it runs `max_concurrent_runs` conversations waits in `_when_there_is_room` (the node shows `waiting_to_start`) until a conversation stops running.

## Settings and limits

`DirectorSettings` (`max_teams` for a team with every team below it, `max_depth`; `GET`/`PATCH /api/director/settings`, kept in `director.json`) are read only by `split.check_limits`, when sub-teams are proposed, when they are approved and again when they are set up, so a lowered limit refuses the next sub-teams and removes nothing.

## Status

A node's status is worked out, never declared (`org_store.status_of`): `blocked` while an escalation its IC raised is unsettled or an agent failed, else `working` while an agent runs (which follows the conversations through `ConversationService.add_execution_status_listener`), else `done` once it has submitted its work and that was not sent back (any review state but `changes_requested`), else `idle` (`blocked` if an agent is lost). The store recomputes it in `set_agent`, `set_review` and whenever escalations change; set a review with `OrgStore.set_review`, not `update_node`, or the status goes stale. `save_org` leaves the running state out, so status flips do not become commits.

## Boundaries

A team is held to its boundary in code, not by its prompt. `DirectorService.guard_action` is asked before every action of every agent through `ConversationService.add_action_guard` and blocks a file tool (`director/boundary.py` lists them and the field that names the file) from writing outside the team's directory, into a sub-team's directory, or anything at all for a Manager; a new file-writing tool must be added to that list. Where bubblewrap works, `director/sandbox.py` also writes one shell script per agent into `<git dir>/director-shells/` and the agent's terminal is started with it (`tool_params` on `start_conversation`/`start_child_conversation`), so the shell's mount namespace has the org's checkouts read-only except the team's own directory and the git directory; `OrgSummary.boundary_enforcement` says which of the two holds. The script is read when a shell starts, so a split narrows an IC's shell only from its next start.

## The human's messages

`POST /api/director/org/messages` is the human's way in: it routes a message to the nearest team above a directory (`boundary.nearest_team`) and, without an org, takes up the one saved in the repository of the `conversation` it comes with or starts one there from the message. A client can therefore offer every new conversation's first message to it. Conversations the director starts itself (Managers and sub-team ICs, not the root IC) carry the tag `startedby=director` (`pods.STARTED_BY_DIRECTOR`, through `extra_tags` on `start_child_conversation`), which clients use to keep them out of the list of the human's own conversations.

## Titles and headlines

Team titles and `headline`s come from one separate model call per team (`director/headline.py`, through `PodLauncher.summarize`), never from the agents' own conversations, and a failed or slow call leaves the name the team has.

## Pruning

A Manager removes a team directly below its own with `prune_team`: `DirectorService._prune` stops and deletes the conversations of the team and of every team below it, discards the uncommitted changes in the team's directory after saving them as a commit under `refs/agents/pruned/<node id>/<time>` (`git.save_and_discard`), and removes the node, so the directory is the IC's above again; that IC is told the Manager's reason. A prune never starts a team, and it waits until no agent of the team or of a team below it is in a turn (`DirectorService._wait_until_quiet`).

## The agents' git

Every IC's terminal is started through a script in `<git dir>/director-shells/`, confined or not, because that script also puts the `git` from `director/git_index.py` first on `PATH` (through a bash `--rcfile`, since `~/.bashrc` may reorder `PATH`). Inside the org's repository that `git` runs the real one on `<git dir>/agent-index-<conversation id>`, where everything outside the team's directory is reset to `HEAD`, marked skip-worktree and ignored, so `git add -A` and `git commit -a` take only the team's own files; it resyncs when `HEAD` or the team's sub-teams change, runs HEAD-moving commands one at a time under `flock`, and after a commit resets the committed paths in the checkout's own index. Do not give agents a bare `GIT_INDEX_FILE`: an index that is one commit behind reverts that commit when it is committed from.

## Specs, contracts and ownership

A team is told its own boundary's `spec.md` and two sets of contracts, nothing else of the teams above: `GitStore.applies_to` returns the spec, the `contracts.md` of its own boundary (between its sub-teams) and the `contracts.md` of the boundary of the team above (between it and the teams beside it). The contracts of an approved split are written to `contracts.md`, not into the spec, so whatever a sub-team must respect has to be in them. `GET /api/director/org/nodes/{id}/ownership` (`director/ownership.py`) lists the files of a node's checkout by the direct report that owns them and the files that conflict when the tips of the checkouts of the node and its reports are merged in memory with `git merge-tree --write-tree`; uncommitted changes are not compared.

## Review

Work a team's IC submits with `submit_review` (refused while anything in its directory is uncommitted, or while its work already waits) ends that IC's turn and is reviewed by the IC of the team above, not by a separate agent and not by a Manager: `DirectorService._request_review` first asks the team's own IC two questions on top of its conversation with `PodLauncher.ask_agent`, which records nothing in it: to write up what the team changed since `OrgNode.base_commit` as a pull request description, and to review it with OpenHands' public `/codereview` skill as instructions (`director/bugbot.py`; `find_review_instructions` is injected so tests never load public skills). No diff is sent to a model; the questions carry only git's list of changed files. Both answers are stored on `OrgNode.review` and sent to the IC above in a review request. Requests are held (the run-state mark `HELD`) so that the IC is woken once: `DirectorService._release_reviews` sends all of a node's held requests in one message when every sub-team has submitted or is `blocked`, at once when that IC is in a turn or starts one, and with an escalation an IC below raises; a paused org sends them on resume. A sub-team that neither submits nor blocks therefore holds back the reviews of the teams beside it until it is told to the IC above as stalled or is stopped (below). That IC decides with `review_team`. An accept merges the tip of a team with its own worktree into the checkout above (`director/merge_back.py`, under the lock the agents' `git` takes) and tells nobody further up unless the IC passed `needed_above`; work that conflicts or reaches outside the team's directory is sent back instead. There is no limit on rejections; `Review.round` counts them, and every `manager_check_ic_escalations` of them on one piece of work wake the Manager above (`request_changes`), as that many escalations do. Each change is reviewed once, by the IC directly above the team that made it: after an accept, `DirectorService._pass_up` looks at the team above, and when all its sub-teams are accepted and it changed nothing itself (`_own_changes`: nothing committed since its `base_commit` or uncommitted in its directory outside its sub-teams') its work is merged into the checkout above and marked `accepted` with no review (`Review.passed_up`), and so on up. A team that did change something, and the top team always, is left for its IC to `submit_review`; a merge that fails on the way up stops there and tells that team's IC. `DirectorService.settled()` waits for effects that effects queue, so a test can assert right after it.

## Memory sync and reports

The team memory leaves the machine only when asked: `POST /api/director/org/memory/pull` fetches a remote's `refs/agents/memory` and merges it, and `.../push` pushes, pulling first only when the remote refuses the push (`director/memory_sync.py`). `GitStore.merge` settles what both sides changed itself: reports become the union, and of any other file the local text is kept and named in `kept_local`. Either agent of a team records decisions, setbacks and reflections with `report`; they are kept per agent in `.reports/<node id>/<role>.json` of team memory, are only ever appended, and are read by the two agents of that team alone (`DirectorService.reports_of`), in `read_node_context` and in a briefing. Nothing is inherited down the tree and the human has no route to add one. When a report takes an agent's past `DirectorSettings.report_compaction_chars` characters (and a quarter of that is new since the last rewrite), a model rewrites them into one report marked `compacted` (`director/compaction.py`); the size is counted in characters because an external agent has no tokenizer at hand.

## Resting an IC

`submit_review` rests the IC: `DirectorService._rest` pauses its conversation after the step it is in (`PodLauncher.pause`) and, in the lane of the team's messages, waits until it has stopped, so that nothing sent to it afterwards lies unread; the next message runs it again. An IC that runs its own tools is not paused, since that would end its process: the tool's answer tells it to end its turn, and one that still runs after `_REST_CHECKS` is cut short with `PodLauncher.stop` (ACP `session/cancel`), which costs it the step it is in. Standing guidance from the human is a convention, not a feature: it goes into the repository's `AGENTS.md`, which every agent reads.

## Messages and proposals

An IC and a Manager talk in free text: `msg_manager` (an IC to its own Manager) and `msg_ic` (a Manager to its own IC, or with `team` to the IC of a team directly below). `DirectorService.message` keeps each message in `.threads/<manager node>/<ic node>.json` of team memory and delivers it through the outbox; `GET /api/director/org/nodes/{id}/messages` returns the threads a node's agents take part in (`threads_of`). An IC proposes sub-teams inside a `msg_manager` text, as one fenced ```` ```teams ```` block of YAML (`split.proposed_teams`: `teams` with `name`, `path`, `instruction` and optional `model`, `writable`, `readonly`, `isolation`, plus `contracts` and `keep`); a team without sub-teams may use `msg_manager` only for that. A block that fails any check (`split.normalize_split`, `check_limits`, the allowed profiles) is refused to the IC and nothing reaches the Manager; one that passes is kept parsed in `OrgNode.pending_split`. The Manager sets the teams up exactly as written with `approve_teams`; any `msg_ic` to its own IC while a proposal waits puts it aside, and a later block replaces an earlier one. There is no count of attempts. An IC never configures a Manager: every team gets one, derived from its IC.

## Replacing teams

Proposed teams may overlap the ones the node already has: a team whose directory equals, holds or lies inside an existing direct sub-team's replaces that sub-team (`SplitProposal.replaces`), and whatever the new teams leave of the directory is the proposing IC's again. An IC that already has sub-teams must say what becomes of each: the block's `keep` lists, by name or node id, every sub-team that stays as it is (`SplitProposal.keeps`), and `split.normalize_split` refuses a block that leaves a sub-team neither kept nor replaced, keeps one it also replaces, or names one the node does not have. Only a proposal's first check asks for `keep`; the checks at approval and at set-up pass none. A proposal never removes a team without replacing it: that is the Manager's `prune_team`. A replaced team's own sub-teams stay and are moved with `OrgStore.move` (which re-routes their escalations) under the new team that holds their directory, else under the proposer; a proposed team may not sit inside such a sub-team, and a team with a worktree of its own cannot be replaced while sub-teams work in that worktree. `DirectorService._carry_out_split` fixes the whole plan in the intent's first step, waits until the replaced teams and their sub-teams are at rest (messages to them stay in the outbox meanwhile), merges what replaced teams committed in their own worktrees into the proposer's checkout (`_take_in`; a conflict declines the approval and changes nothing), saves their uncommitted work under `refs/agents/pruned/`, removes them and sets the new teams up.

## Starting teams

Setting teams up starts nothing: a new team has no agents (`OrgNode.agents` is empty) and its `instruction` is kept as what it is for (the run-state mark `TASK`). Its IC is added and started by the first thing sent to it (`DirectorService.tell_ic`: a `msg_team` from the IC above, a message from the human, a review request for a sub-team moved under it), with that message as the end of its briefing; send to an IC through `tell_ic`, never by looking its conversation up. A team that was never started owes nothing: it cannot stall, holds back no review of its siblings and does not keep the team above from going up (`_may_stall`, `_release_reviews`, `_pass_up`). An agent is derived from the nearest IC at or above its team that has started (`_started_ic`). Teams waited for are kept in memory only (`_settling`) and found again when the step is carried out again. A Manager is woken by its briefing, a `msg_manager`, an escalation from below, a team its IC stopped and the two checks below; nothing wakes it when a sub-team is `blocked` or when approved teams cannot be set up: its look says how long a blocked team's IC has waited, and a set-up the runtime refused is kept in the record as `declined` (`_decline`), where it reads it.

## What a removed team leaves

A team that is removed, by a `teams` block that replaces it or by `prune_team`, leaves nothing a later team finds by accident (`DirectorService._archive`, called before `store.remove`): `GitStore.record_former` writes one record `.former/<node id>/<time>.json` (`FormerTeam`: title, directory, purpose, how it ended, its review, its reports in full and as one report a model shortened, the contracts between its sub-teams, its message threads) and in the same commit deletes its reports, its `contracts.md` and every thread it took part in; the run-state marks `TASK`, `PROGRESS` and `CHECKS` of its node id are cleared. This matters because a node id comes from the directory, so a new team in the same directory has the old team's id. Recording a removal again changes nothing, which is what makes the step safe to carry out twice. Only `spec.md` stays where it is: a new team is marked with the specs it finds in its directory (`OrgNode.old_specs`, set in `_specs_left_in` for a team's own directory and for the directories of replaced teams that hold it or lie in it; after a prune, on the team above), `DirectorService.specs_of` returns them with `old` and `left_by`, briefings and the context (`specs_left_by_teams_before_you`) say they are old, and `write_spec` clears the mark. Reports belong to an agent of a team, not to a conversation: `.reports/<node id>/<role>.json`. Sub-teams of a replaced team that was stopped go on under the team they are moved to (`_go_on(own_too=True)`), with their time without progress started again.

## Managers and their looks

A started team has its IC alone. Its Manager is added to `OrgNode.agents` and started by the first thing sent to it (`DirectorService.tell_manager`: a `msg_manager` or an escalation a Manager below raised), briefed with the team's task from the run-state mark `TASK`, so send to a Manager only through `tell_manager`. The director also wakes a Manager to look at its teams on two counts kept apart in the run-state mark `CHECKS` (`DirectorService.count_accepted_review`, `count_ic_escalation`): every `DirectorSettings.manager_check_accepted_reviews` (default 5) reviews its IC accepted with `review_team` (work that went up by itself in `_pass_up` is not counted), and every `manager_check_ic_escalations` (default 3) escalations that the IC of one team directly below raised or passed up to its IC on the work that team has in hand. Each count starts again when it wakes the Manager and neither touches the other; a team's escalation count also starts again when its work is accepted (`_work_accepted`), since what it does next is other work, so the count belongs to a team and a piece of work, not to a team for good. 0 turns a check off. The wake-up (`prompts.manager_check`) lists the teams below with their status, review, escalations and time without progress, and asks for nothing.

## Stalls and stopping

Teams that get nowhere are found by time, not by counting rejections. The director keeps when each team last got anywhere in the run-state mark `PROGRESS` (`DirectorService.progressed`: its start, a `submit_review`, a review decision, an escalation raised or settled, an accept of one of its sub-teams, a `msg_team` to it; and a new commit under its directory, which `_check_stalls` finds with `git.last_commit_in`). Every `STALL_POLL_SECONDS` `_check_stalls` looks at each team that owes work nobody is waiting to give it (`_may_stall`: not submitted, or sent back; not `blocked`, not under a stopped team) and, after `DirectorSettings.stall_check_minutes` (default 120, 0 turns it off) without progress, tells the IC above once, and once more for each further such stretch: `prompts.stall_notice` carries how long, what the team's own IC answers when asked on top of its conversation (`STALL_QUESTION` through `ask_agent`; not asked while it is in a turn) and the git commands to look for itself, and the reviews held for that IC are released with it. The first notice about a team counts as progress of the team above, so that IC has one stretch to act before it is told on itself. The clocks start again when an org is resumed and when a server starts; the clock is injected (`clock`, `stall_poll`) and tests call `_check_stalls` themselves. An IC writes to the IC of a team directly below with `msg_team` (`DirectorService.message_team`, kept in `.threads-ic/<its node>/<the team>.json` and returned by `threads_of` as a `Thread` with `ic_to_ic`); nothing goes back up that way, the team answers through its work or an escalation. As a last resort an IC stops a team directly below with `stop_team`: `OrgNode.stopped` (set with `OrgStore.set_stopped`, which makes the status `blocked`) records why and which conversations were in a turn, the agents of the team and of every team below it are paused, `_deliver` holds everything sent to them in the outbox (the human's words too), and the Manager of the stopping IC's team is told. A stopped team goes on when that IC writes to it with `msg_team` (`_go_on` delivers what waited in the order it was sent and runs the agents that were cut off), can be replaced through a `teams` block and can be pruned by the Manager like any other team; the human has no control to stop one.

## Context

An agent is told its team's context without asking. `DirectorService.context_of` builds it (it is also what `read_node_context` returns), a briefing ends with the parts it does not already say in its own words (`context.briefing_block`), and what the agent was told is kept per conversation in the run-state mark `TOLD`. A change to the context never sends a message, since every message starts a turn: `_deliver` compares the context with what was told (`_with_what_changed`) and appends a `[director] context update` block to whatever message goes to that agent next, the human's included. `context.steady` leaves out what comes and goes with every turn (`working`/`idle`, headlines), a list that only grew is told as what was added, the list of sub-teams is told as the teams that changed or went (`context._teams_changed`), and an agent is not told back its own reports or the escalations it raised. A system prompt cannot carry this: it is fixed when a conversation starts and derived agents inherit their parent's. Add a field to the context in `context_of` and it reaches briefings, updates and the tool alike. A model call the director makes for itself, apart from any conversation, goes through `PodLauncher.ask` with its own `usage_id`.

## Unfinished work and recovery

The director's unfinished work is kept outside git history, in the SQLite file `<git common dir>/director/state.db` (`director/run_state.py`): which agents were running, which teams wait for a run slot and in what order, the multi-step actions it began (intents) and the messages it has not delivered. A multi-step action goes through `DirectorService._begin`, which records it before its first step; `_carry_out` runs the `_do_<kind>` handler, which marks each finished step with `run.step_done` and skips marked steps, so every handler must be safe to run again. Messages to agents go through `_post`/`_send` (held, then delivered: at least once). `POST /api/director/org/pause` and `/resume` stop and continue all of it, `GET /org/recovery` says what a resume will do; a server that starts with unfinished work loads the org paused (`shutdown` or `crash`) unless `DirectorSettings.resume_on_start` is set. `director/recovery.py` drops run state that no longer fits the tree (another server's file, a team changed or removed since) and names what it dropped. Finished intents and delivered messages are deleted, so the file holds only what is open.

## Inheritance, hand-over and the record

What a team inherits from the teams before it is decided, so keep to it: nothing by itself. A team is cleared, split or merged only through a `teams` block and removed through `prune_team`; there is no merge or re-parent command, and a clear is simply a different team proposed for the same directory. What the removed teams left is given to the IC that proposed the change, or to the IC above a prune, in hand-over mode: a side conversation of that IC which the director starts for that hand-over alone (`DirectorService._do_hand_over`; it is no agent of its own but `AgentRef.hand_over` on the team's IC, found by `OrgStore.find_hand_over`, derived from the IC's conversation and briefed by `prompts.hand_over_brief` with each team's reports as one report, in full, the contracts between its sub-teams, its spec, who has its directory now, and the team's own context). It shares nothing with the IC's main conversation, which is only told that it runs and, when it ends, what it did (`handed_over_notice`); its status does not count toward the team's, it edits no files, and of the director's tools only `read_node_context`, `hand_over` and `write_spec` work in it. Each hand-over gets a new one, which replaces the one before; where it cannot be started it is tried once more, and then the mode stays on the IC with the status `lost` and the IC's main conversation is told so and nothing more, by decision: the job is not moved there. A hand-over conversation is paused, run again and read back after a restart as an agent's own is (`recovery.put_aside_stale` keeps its marks, `_resync_hand_overs` ends one that finished or was lost meanwhile). That IC decides which team gets what with the `hand_over` tool (`DirectorService.hand_over`: notes are appended to the team's IC reports as a `Report` with `handed_over`, which a briefing and the context show as written by the IC above; contracts replace the team's own `contracts.md`). `hand_over` starts nothing, nothing waits on it, and it can be repeated; `read_node_context` returns the records again for an IC (`former_teams`, in full only from the tool; the context told with every message only names them). The hand-over conversation is told to rewrite the team's spec, and the answers of `approve_teams` and `prune_team` tell the Manager it may need to explain the change with `msg_ic`. The `contracts` of a block that replaces teams take the place of the node's `contracts.md`; a block that replaces none adds to it. What became of the teams directly below a team is kept in team memory as `TeamEvent`s (`.history/<node id>.json`, `GitStore.append_history`, written by `DirectorService.record_event`: set up, accepted, sent back, stalled, stopped, replaced, pruned, and each time the Manager was woken with the reason). It outlives the teams it is about; a team's own file goes with it when it is removed. Both agents read it through `read_node_context` (`track_record_of_the_teams_below`), a review request carries the team's record, and `manager_check` lists it, with the teams that are gone. It is not part of the context told with every message, so it adds no context update. A team that was set up and given no task for `stall_check_minutes` is told to the IC above once and not again, since a team may wait on purpose (`prompts.unstarted_notice`, from `_check_stalls`); it is not a stall and is not recorded as one. The memory route returns the removed teams and the record for a client (`NodeMemory.former_teams`, `NodeMemory.history`). `GET /api/director/org/history` returns the records of all teams as one list, newest first (`DirectorService.org_history`, without the `needed` events). How teams are split, merged and pruned is decided, so keep to it. An IC splits by concern first (one thing a team can own behind a short contract) and for efficiency; teams working at the same time follow from that and are not a reason to split (`POD_PROTOCOL`). A proposed team and the block may carry an optional `reason` (`SplitChild.reason`, `SplitProposal.reason`). The director adds to a proposal, for the Manager, what it knows (`DirectorService.facts_of_proposal`, `prompts.proposal_facts`): files in each directory, commits that changed two proposed directories together, and teams that had a directory before with why they were pruned. Proposals and approvals are kept in the record (`proposed`, `approved`). A Manager declines what its IC proposed with `decline_teams` and a reason (`pod_actions.decline_teams`), which is kept as `declined` with the proposal's directories (`TeamEvent.paths`) and told with a later proposal for the same directories; a message with `msg_ic` decides nothing, and what was proposed waits on the Manager until it approves or declines or the IC proposes again. A Manager is woken only by the two counts it had (accepted reviews, and one team's escalations on the work in hand); work that is sent back is recorded, and wakes the Manager once it was sent back as often as that number. When the escalation limit is reached the `woken` event names the team, and `track_records` counts for each team its tasks and the ones on which that limit was never reached; `manager_check` tells the Manager that as the team's success rate (`success_rate`, with `success_rate_meaning` naming the number from the one setting `manager_check_ic_escalations`). Token use is deliberately not a measure of a team: tasks differ in difficulty. A Manager may prune any team directly below; the runtime refuses none on its record, by decision. It is told to prune only a grossly inefficient team, that it is never obliged to, and to wait until a team has had enough tasks to judge it by; how many is its judgment and deliberately no setting. What says that two teams should be one is counted, not guessed: a write by one team's IC that the runtime refused because the file is a sibling's (`guard_action`), and a review finding on one team's work that names a sibling's file (`request_changes`), are kept as `needed` events with the other team (`DirectorService.record_need`, `TeamEvent.other_id`, the same file and way once, which is looked up in the record itself and so holds across restarts). `prompts.needs_between` counts them for each pair of teams that are there, from the time each was set up. From `NEEDED_WORTH_SAYING` (3, deliberately no setting) the IC is told in a review request for either team and by `read_node_context` (`teams_below_that_needed_each_other`); a Manager is told any count when a proposal replaces both teams. It wakes nobody, merges nothing, and is by decision not part of a Manager's look. Escalations that merely name another team are not counted: a text match can be wrong. The human still cannot prune, replace or split.

## Exchanging an org with a remote

An org is exchanged with a remote of its repository only when asked, as git does a branch: `POST /api/director/org/push` and `/org/pull` (`director/org_sync.py`) move `refs/agents/org`, `refs/agents/memory` and the branch of every team with a checkout of its own, kept on the remote as `refs/agents/teams/<node id>`. A pull is a merge (`director/org_merge.py`, a pure function over saved nodes): a team or a field changed on one side only is taken from that side; the same field changed on both, a team removed on one side and changed on the other, and a spec or contracts both rewrote in the same lines are conflicts. With conflicts nothing is written, the org stays paused, the merge is kept in the run state and `GET /org/merge`, `POST /org/merge/resolve` and `/org/merge/abort` settle it; finishing writes a commit with both parents. `worktree_path` and `agents` belong to the machine that runs a team and are never taken from the other side (`LOCAL_FIELDS`). Agents' conversations do not travel: after a pull into another clone every agent is `lost`, and `POST /org/nodes/{id}/start_again`, or a message that comes with a conversation, starts a team afresh in its own checkout. Without a conversation `start_again` starts the team's IC like the IC of the team above (or from the team's own agent profile), so the top team is started first and the others top-down. `tree-stream` carries `paused` and `merging` in its snapshot and an `org_state` event on every change. The intents `accept` and `request_review` are forgotten only after the tree they changed is saved, so a server that ends in between does them again; an `accept` found already accepted still does what follows it (`_pass_up`).

## The human's edits

The human reads and changes a team's files through `director/changes.py`: `GET /api/director/org/nodes/{id}/changes` lists what differs in the team's directory from `OrgNode.base_commit` (uncommitted and new files included), `.../changes/file?path=` gives both sides of one file, and `PUT .../files?path=` writes one file, commits it alone as `Edited by hand: <path>` and tells the team's IC, which starts a turn of it. The write is held to what the team's own agents may write (`changes.edit_refusal`, the same rules as `boundary.write_refusal` worded for a person) and is refused with 409 while an agent of the team is running. There is no shell for the human.

## ACP processes

An `ACPAgent`'s command is started in a session of its own (`start_new_session`), and closing the agent signals the whole process group, then kills what is left of it after `_ACP_GROUP_EXIT_GRACE_SECONDS`: the command is usually `npx`, which starts `node`, which starts the agent. Test stand-ins for the process set `pid = None` so that closing has no group to signal. The director's `sandbox.command_script` adds bubblewrap's `--die-with-parent` for an agent's whole process, not for a terminal's shell (`shell_script`): the kernel counts the thread that started a process as its parent. A message to an ACP agent in the middle of a turn ends that turn, so `DirectorService._deliver` leaves the director's own notices in the outbox while such an agent runs and `_note_running` delivers them when its turn ends; only what the human said (`route_message`, `answer_escalation`) is posted with `at_once=True`. The intent `finish_split` is saved before it is forgotten, like `accept`.
