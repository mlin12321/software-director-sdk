# The director

See the [project root AGENTS.md](../../../../AGENTS.md) for repository-wide policies.

The director keeps an org tree of agent teams and a team memory, and runs the teams' agents, an IC and a Manager each, in sessions. It is code with fixed rules, not an agent. What follows is decided; keep to it when changing the module.

## The service is a package of layers

`DirectorService` is one class built as a chain, one module of `director/service/` on the next: `state.py` (`ServiceState`: the tree, the settings, the run state, the queue of steps, saving, the agents' shells, and the module-level constants and helpers more than one layer uses), `records.py` (what is read and kept of the teams), `delivery.py` (messages, waiting for quiet agents, model calls), `teams.py` (starting agents, what teams are sent), `requests.py` (choosing the team a request goes straight to), `reviews.py`, `watch.py` (stalls, stops, and handing an escalation to the agent that has it), `splits.py` (splits, pruning, hand-over), `sessions.py` (opening and closing sessions), `sync.py` (pause, resume, pull, push, merge) and `__init__.py` (`DirectorService`: `start`, `create_org`, `route_message`, `guard_action`, and the table of steps). A method calls only what its own module or one below it defines. Put a new method in the lowest module that has what it calls; do not import a module above. Three things point upward on purpose and are overridden above: `ServiceState._steps` (the steps by kind of intent), `ServiceState._came_back` and `Requests._hand_on` (where a request that is not a team's goes, which `Sessions` decides for a session's opening place).

## Org tree and team memory

The director (`openhands-agent-server/openhands/agent_server/director/`, routes in `director_router.py` under `/api/director`) keeps an org tree of agent teams and a team memory in hidden git refs (`refs/agents/org`, `refs/agents/memory`) of the org's repository. That is the git repository of the workspace of the org's first conversation, wherever the server was started: `create_org` moves `DirectorService._repo_dir` there and writes it to `director.json` beside `Config.conversations_path`, which is read first on the next start. Until there is an org, the director looks in `Config.director_repo_path` (default `workspace_path`). A repository that has no org and is a git submodule stands for the nearest repository above it that has one (`DirectorService._load_from`), both at startup and when a first message arrives; `OrgSummary.repo_path` is the org's repository and `OrgSummary.directory` is where the server's own directory sits in it, which is where a message without a `path` is routed from. Tests that start an org through the app must point `conversations_path` at a temporary directory, or `director.json` leaks between them. `GitStore` never touches the working tree or the user's index: it builds trees in a throwaway `GIT_INDEX_FILE` and lands them with a compare-and-swap `git update-ref`, retrying when another writer wins. `OrgStore` owns the derived `child_ids` and is the only emitter of org events; mutate the tree and the sessions through it. A stream subscriber follows one focus team plus the teams it has expanded (or the whole subtree with `full`), and gets the open sessions and the list of escalations that wait on the human, of every session whatever its focus, whenever either changes.

## Escalations

An escalation is raised at a place of a session and goes up inside that session: it is held by the place above the one that raised it and moves only through `OrgStore.pass_up_escalation`, one place at a time with a reason, so `held_by` is `None` only after every place above has passed it up (the store rejects anything else). The chain ends at the place the session was opened at (`OrgStore._chain` stops at the Division Lead place), so what that place raises or passes up waits on the human. Keep it that way when adding ways to raise or route escalations. Escalations run in two lines: `Escalation.raised_by` is the role of the agent that raised it, and at each place it is that role's agent that is told (`Watch.hand_escalation`) and that may settle or pass it up with `resolve_escalation`, so an IC's goes IC to IC and a Manager's Manager to Manager; the human's answer goes to the agent that raised it. The wire types are mirrored by hand in `clients/typescript/src/models/director.ts` (client-ahead of the pinned release); change both together. `DirectorService` loads nothing until first use, so `create_app` stays free of git calls.

## Agents are conversations

An org's agents are ordinary conversations: `POST /api/director/org` starts the IC of the org's first session from the caller's `StartConversationRequest`, as does any request that comes with a conversation, and every other agent is derived from an existing one with `ConversationService.start_child_conversation` (a Manager from its team's IC, a sub-team's IC from the IC above, a session's IC or Division Lead IC from an IC that runs already: `_derived_from`, `_template`), so model configuration and secrets stay in the conversation store and never reach the org ref. The director reaches conversations only through `TeamLauncher` (`director/launch.py`), which tests replace with a fake.

## Agents that run their own tools

An agent that runs its own tools (an `ACPAgent`: Claude Code, Codex) can be any agent of an org, the IC a session starts with included. It cannot be given the director's tools in-process and its tool calls never pass `guard_action`, so `DirectorService._adapter` changes it as its conversation starts (the `adapt_agent` hook of `start_conversation` and `start_child_conversation`): `mcp_config` gains the stdio MCP server `director/mcp_shim.py` (standard library only, run by its path), which lists the tools from `GET /api/director/tools` and passes each call to `POST /api/director/tools/{name}`, and `acp_command` is prefixed with `<git dir>/director-shells/<conversation id>.acp.sh` (`sandbox.command_script`), which starts the agent's whole process in the team's sandbox with the team's `git` first on `PATH`. Those two routes are mounted outside the session-key dependency: the caller is known only by `X-Director-Agent-Token`, an HMAC of its conversation id (`director/acp.py`) with a key kept in `director.json`, so it survives restarts and never reaches the org ref. They run the same `agent_actions` as the in-process tools (`director/tools/remote.py`); add a tool to `DIRECTOR_TOOLS` and to the role that may use it in `service.TOOLS_OF`, and both ways get it. Which tools an agent has is `service.tools_of(node, role)`: its role's, or at a Division Lead place `DIVISION_LEAD_IC_TOOLS` for the IC and `DIVISION_LEAD_MANAGER_TOOLS` for the Manager. A tool's free text is named `text` in every tool; name a new tool's the same. An agent is offered only those tools: `DirectorService._adapter` puts them in place of the ones a derived agent carries from the agent it was derived from (a Manager from its IC), `GET /api/director/tools` lists them for the caller, and `tools.remote.call_tool` refuses a call of a tool the caller is not offered; `agent_actions._only` stays the check of the role. What an agent always reads is kept short, so keep to it: `ORG_PROTOCOL` holds what every IC needs from its first turn, `MANAGER_ROLE` the Manager's part, which only a Manager is given, and what concerns a rarer event is said in the message that brings it (`review_request`, `stall_notice`, `approved_notice` with `WITH_SUB_TEAMS`, the hand-over brief, `manager_check`). Put new guidance in the message of the event it is for, not in the protocol. The shim needs the server's own address: `director_server_url`, or else the base URL of the director's last request. Without bubblewrap nothing holds an ACP agent's process, so its IC always gets its own worktree and what it commits outside its directory is refused at merge-back; `SessionTeam.boundary_enforcement` says which holds per place (`sandbox`, `checks`, `merge`), and an ACP Manager is then held by its prompt alone. A proposed sub-team may run on another agent with `model` in its proposal (`propose_teams`) (`SplitChild.agent_profile`), a name from `DirectorSettings.allowed_profiles`; that team's IC is started from the stored profile with `TeamLauncher.start_from_profile` as a child of the IC above, its Manager derived from it as always. The director asks an ACP agent in one of two ways, since it has no model the server can call. A question that needs nothing of the agent's conversation (`TeamLauncher.summarize` and `ask`: a team's title and headline, where a request goes, reports rewritten shorter) is a side question: a new, empty session of the agent's own ACP process, without the director's tools, that is prompted once and closed (`ACPAgent.ask_aside`, `ConversationTeamLauncher._ask_aside`), so it can be asked before the agent's first turn and pays for none of its context. A question on top of the agent's conversation (`TeamLauncher.ask_agent`: what a team changed, why it stalls) forks its session, and Claude Code cannot fork a session that has had no turn. Both are recorded as the agent's use, what the side session reports it cost included, and one that does not answer within `_SIDE_QUESTION_TIMEOUT` is cancelled alone. The conversation of an agent of the org cannot be forked (`conversation_router._not_an_agent_of_the_org`): a copy would act as that agent, in no team. An agent is never derived from a Division Lead IC (`Teams._started_ic`), and none is started in a team a step is replacing or removing (`_start_new`). A session the human gave no name is called by the title a model makes of its request: with the top team for the org's first session (`_summarize` with `rename`), and by itself for a session opened at a team the org has, which keeps its own name (`Delivery._name_session`).

## Tools and effects

Agents act on the org through the tools in `director/tools/`, which run in-process: a tool resolves its caller with `OrgStore.find_by_conversation`, `director/agent_actions.py` checks the caller's role and place, and anything that touches a conversation (starting agents, sending messages, saving the tree) is queued with `DirectorService._enqueue(effect, lane)`. Effects of one lane run in order and lanes run side by side: a place's id for its starts and messages, `review:<id>` and `headline:<id>` for its model calls, `org` for saves. An effect that must follow another has to share its lane. Keep it that way: tools run on agent threads and must not wait on a conversation, and nothing may call back into the store from a store listener. A start the server refuses because it runs `max_concurrent_runs` conversations waits in `_when_there_is_room` (the place shows `waiting_to_start`) until a conversation stops running.

## Settings and limits

`DirectorSettings` (`max_teams` for a team with every team below it, `max_depth`; `GET`/`PATCH /api/director/settings`, kept in `director.json`) are read by `split.check_limits`, when sub-teams are proposed, when they are approved and again when they are set up, so a lowered limit refuses the next sub-teams and removes nothing; `Reviews._check_placement` holds a team a Division Lead Manager moves to `max_depth` as well. A session is counted where it is in the org: levels from the org's top team, and teams for the proposing place, every place above it in the session and every org team above the one the session was opened at.

## Status

A place's status is worked out, never declared (`org_store.status_of`); a tree team has none. It is `blocked` while the place is stopped, an escalation its IC raised is unsettled or an agent failed, else `working` while an agent runs (which follows the conversations through `ConversationService.add_execution_status_listener`), else `done` once it has submitted its work and that was not sent back (any review state but `changes_requested`), else `idle` (`blocked` if an agent is lost). An agent that is `blocked` or `lost` carries why in `AgentRef.reason` (`TeamLauncher.failure` reads the conversation's last `ConversationErrorEvent`; a start that failed keeps its error), and it is told, never only shown: `Teams.tell_of_failure` records the event `failed` and calls `Teams.tell_above`, which tells the IC of the team above, or, where no IC works above (the team a session was opened at, and its Division Lead place), raises an escalation that waits on the human (`failure_waits(role)`; `STALL_WAITS` for a team without progress). The human's answer goes to that agent and runs it again, or starts the team again when the agent is lost; the escalation is settled by itself once the agent runs (`Sync._runs_again`). A step of the director that raises is kept as a `failed` event too (`Records._keep_failure`). Use `tell_above` for anything else that is wrong with a team and that somebody must hear of. The store recomputes it in `set_agent`, `set_review` and whenever escalations change; set a review with `OrgStore.set_review`, not `update_place`, or the status goes stale. `session_state._kept` leaves the running state out of what is kept of a place; it is read back from the conversations on load.

## Boundaries

A team is held to its boundary in code, not by its prompt. `DirectorService.guard_action` is asked before every action of every agent through `ConversationService.add_action_guard` and blocks a file tool (`director/boundary.py` lists them and the field that names the file) from writing outside the team's directory, into a sub-team's directory, or anything at all for a Manager; a new file-writing tool must be added to that list. Where bubblewrap works, `director/sandbox.py` also writes one shell script per agent into `<git dir>/director-shells/` and the agent's terminal is started with it (`tool_params` on `start_conversation`/`start_child_conversation`), so the shell's mount namespace has the org's checkouts read-only except the team's own directory and the git directory; `OrgSummary.boundary_enforcement` says which of the two holds. Inside the git directory the director's own files (`director/`, `director-shells/`) and the hooks git runs for everyone (`hooks`) stay read-only, while git's `config` stays writable, and `director.json`, which holds the key of the tool tokens, cannot be read. A team's folder that is reached through a link opens nothing: the shell does not start. A guard that raises blocks the action (`EventService._guard_action`); an action nobody checked does not run. The agent's `git` (`director/git_index.py`) follows a leading `-C`, refuses to run on an index it could not bring up to date, and undoes a commit that changes a file outside the team's folder (`commit`, `cherry-pick`, `revert`, `am`), in a shared checkout and in a team's own worktree alike. A change by hand (`changes.write_by_hand`) takes the same lock and brings the agents' indexes up to date (`merge_back.bring_up_to_date`), and does not write through a link. The script is read when a shell starts, so a split narrows an IC's shell only from its next start. A sub-team's directory is closed to the IC above from the moment the team starts (`SessionTeam.agents` is not empty), not from the split: until then the IC may finish what it has there, though its `git` commits nothing in it, and `approved_notice` tells it how the split changed its work and which files it left uncommitted in each new directory (`_split_effects`). What it leaves is the team's: `_do_start_team` names the files in the team's briefing (`left_for_team`) and `_pass_down` moves them into the team's own checkout when it has one (`git.bring_over`, kept at `refs/agents/left/<team>`); `submit_review` refuses the IC above while files in a sub-team's directory are uncommitted. A shell that was running before the team started is not narrowed, so what an IC writes from it into a started team's directory is taken out of its checkout when that team's work is accepted (`_put_aside`, kept at `refs/agents/aside/<team>/<time>`) and the IC is told.

## The human's messages

`POST /api/director/org/messages` is the human's way in: it opens a session for the message at the nearest team above a directory (`boundary.nearest_team`), or with `session_id` says it in that session, and, without an org, takes up the one saved in the repository of the `conversation` it comes with or starts one there from the message. A client can therefore offer every new conversation's first message to it. Conversations the director starts itself (every agent but an IC that runs as the conversation a request came with) carry the tag `startedby=director` (`launch.STARTED_BY_DIRECTOR`), which clients use to keep them out of the list of the human's own conversations.

## Requests that go straight to a team

A message sent with `auto` (`RouteMessageRequest.auto`) may go to a team below the one its directory gives, without the ICs between taking a turn. What is decided here; keep to it. The rule behind all of it: a wrong team beside the right one costs more than a team too high, so every doubt moves the choice up and never sideways, and since nobody confirms the choice, an unsure one leaves the request where it was made. `director/routing.py` is pure and decides (`choose`); `service/requests.py` gathers what it decides from (`Requests.choose_team`). Two things say which teams a request concerns: the tracked files and directories its text names (`paths_named`; a bare word that is a directory's name does not count), and a model that is shown a card of each team (inside a session, of each started one) and is asked twice with the teams of each level in the opposite order. The choice is the lowest team that holds every team named (`lowest_holding`), moved up, inside a session, to the first place that can take a request (`takes_requests`: started, not stopped, its IC not lost, its work not waiting for review, since such a team would go on changing what is being reviewed). It is sure only when both answers give the same team, every named path's owner is at or below it, and the team whose card clearly shares most words with the request (`best_by_words`) is on one line with it; named paths alone are sure when the model gives no usable answer. Agreement is the measure: never use a confidence the model states of itself. A request that names a file of a team outside the team it was made at goes no lower than that team, whatever the model answers: it is for a team above both. An answer that names an unknown team is no answer. A card (`Card`) holds only what the director holds of a team (title, directory, the task the IC above gave, the names at the top of its directory, the last requests it took), never its spec or reports, so no team can write itself into more requests. A request that went straight to a team is kept with its session until the session's work is accepted (`Records.keep_routed`) and then for the org in `.routed.json` of team memory (the last 200) and as an `asked` event in the record of the team above; every IC above the team has it in its context as `asked_directly_of_teams_below` (told with the next message, waking nobody, and only what is new of it: `context._LATEST`), and the review request quotes what was asked since the team's work was last accepted (`Records.asked_of`, by the order of the record, not by time, which is kept to the second). A team whose IC says the request is not its own calls `raise_escalation` with the category `misrouted`: that is no escalation and blocks nobody; `Requests.not_ours` hands the request to the IC of the team above, keeps a `misrouted` event, and the last ten are shown to the model. `DirectorSettings.route_requests` turns all of it off. Do not add a way to send to a team the director chose without the checks above, and do not route what is written to one agent or one team on purpose.

One team's IC never asks another's directly. What it needs of a team that is not above it is an escalation like any other: it goes to the IC above, which owns the contracts between its teams and has `msg_team`.

## Sessions

**Only sessions have agents.** A team of the org tree (`OrgNode` in `OrgStore._nodes`, `OrgStore.teams`, `org.json`) is the reference a new agent is briefed from: directory, boundary, spec, contracts, records, sub-teams. It has no agents, status, review, escalations or pending split, and `tell_ic`/`tell_manager` do nothing at a tree id. All work is done in sessions (`service/sessions.py`); the first request to an org opens the first one at the top team (`create_org` returns `OpenedSession`), and every later request opens another (`POST /api/director/org/sessions`, `route_message`).

- **Places.** A session has a place (`SessionTeam`, `OrgStore._places`, id `<team id>@<session id>`) at the team it was opened at and at each team below, each with its own agents, status, review, escalations and pending split. `OrgStore.get` returns a tree team or a place, `team` only the first and `place` only the second; the tree is read with `teams`, `sub_teams`, `teams_above` and changed with `update_team`, `move`, the places with `places`, `below`, `above`, `instance` and `update_place`, `move_place`. `org_store.team_id_of`/`git_store.team_key` give the team a place is of, which is what records are keyed by. A plain team id an agent names in a tool resolves to the place of its own session (`agent_actions._team_named`).
- **Division Lead place.** Nobody stands above a session's opening place, so the session has one more place at the team above (the top team itself for a session opened there): `division_lead_id`, `division_lead`, `parent_id` None, the repository checkout, nothing writable. The opening place's `parent_id` is the Division Lead place, so the review code needs no special case. Its IC is started on demand, only by `tell_ic(..., division_lead=True)` from `_release_reviews`, as the Division Lead IC (`DIVISION_LEAD_IC_TOOLS`, `DIVISION_LEAD_IC_ROLE`): it reads, reports and uses `review_team`. Places below the opening place are reviewed by the session's IC one level up, which gave the task.
- **Where a session is kept.** In the machine's run state only (`run_state.SESSION`, `session_state.py`), never in `org.json` or the team memory, so it is not exchanged with other machines: `org_persistence.reference` saves a tree team with its own fields only, and `session_state._kept` saves a place with its session. Its conversations stay, so a session resumes.
- **Checkout.** The opening place always works in a git worktree of its own (the given conversation with `worktree=True`, a derived IC from the repository's HEAD via `base=`); places below follow their team's isolation.
- **Routing.** A request written to a named team opens the session there; one written to the org as a whole is routed by `choose_team` (`auto`). What is typed in a session's conversation goes to that conversation.
- **Accepts in order, reconciled.** `Reviews.check_accept` refuses an accept while work submitted earlier at the same place waits (`Review.seq`, a counter from `RunState.count`, not a timestamp), and asks the reviewer to reconcile (`reconciled`) when what the session did meets what was accepted meanwhile: files (`_to_reconcile`), specs (`specs_to_reconcile`) or a spec it wrote for a team the org lost (`specs_inherited`). What the reviewer says holds only for what it was shown: `_to_reconcile` returns a mark of what it compared, kept as the run-state mark `SHOWN`, and an answer given when the mark has changed shows the reviewer the new state instead (`_not_reconciled`). A session is never made to catch up while it works.
- **One lane for what the org shares.** Everything that writes the repository checkout for a session, `refs/agents/org` or `refs/agents/memory` runs in the lane `BASE_LANE`, one thing at a time in the order it was asked for: the accept of an opening place's work (`accept` with the payload flag `base`, `_lane_for`), `_pass_up` of one (`_in_base`), `land_org`, closing a session's waiting work, taking in a pulled org, `_name_org`, and rewriting the org's reports shorter. There is no landing lock. `ServiceState._weighing` only guards reading and changing a merge record; agent threads write nothing shared.
- **A change after an accept is said once.** A session whose work is accepted and that then sets up, replaces, moves or prunes a team, or writes a file of team memory, has changed what only another accept gives the org. `Records._note_change` remembers the session (`ServiceState._changed_since_accept`), and when it is next at rest (no place working, no hand-over under way) `Sync._remind_to_submit` tells its IC to submit again (`prompts.CHANGED_SINCE_ACCEPT`), once until the next accept. Commits of code alone are not noticed.
- **A session's own records.** Everything a session changes of team memory is its own until its work is accepted, kept in the run state with what it was written over: files (`FILES`: `spec.md` and `contracts.md` by session and path, text and base; `Records.drafts`, `_draft`, `read_file`), reports (`REPORTS`, each with an id) and the records of teams it removed (`FORMER`). `specs_of`, `contracts_of`, `reports_of` and `former_teams_of` show a session its own over the org's. Contracts of a split, what `hand_over` passes on, and `_archive` all write there, never to team memory.
- **A file that cannot be written.** `_commit_landing` returns the files of team memory that changed while a landing was made. They stay the session's drafts and the Division Lead IC is told (`prompts.files_not_written`); the next submit shows it both texts.
- **What lands on accept, in two parts.** The code part (code, specs, and the reports, events and routed requests of teams the org has) lands on the Division Lead IC's accept. The org part (teams, team fields, contracts, and the records of teams the session set up) lands when the Division Lead Manager has settled what waits of it and every session that submitted earlier has landed its own (`Reviews._in_order`, `_org_turn`). Later work's code is never held up by an earlier Manager; its teams and contracts are. When the org part has nothing open and is first in order, both land in one step (`_land_accepted` → `_land(top, seen, org)`): `ServiceState._commit_landing(tree=True)` stages a commit for team memory and one for the tree (`GitStore.stage`) and moves both refs in one `git update-ref --stdin` transaction (`git_store.swap_together`). Otherwise the code part lands with `waits`/`held` naming what stays the session's, `Merge.code_landed` is set, and the rest follows as the intent `land_org` (`_do_land_org`), replayed after a restart. Each file is settled three ways (base, the session's, the org's now): written where the base still stands, nothing to do where the org has the same, and otherwise a conflict. A report, an event and a routed request are added once, by id. Other sessions read what landed in their next context update; nobody is woken. A landing holds `_saving` from its first change of the tree to its commit (`_land`), so a save of the tree that falls in between waits and the tree never moves without team memory.
- **Team identity.** `OrgNodeInput.since` is when a team was set up. An id comes from the directory, so two teams can have one id; they are the same team only with the same `since` (`Records.is_orgs`). A place whose team the org does not have, or has another team in place of, is not the org's team: it does not read that team's reports, and nothing it wrote lands on that team.
- **Nothing a session wrote is dropped on accept.** What it wrote for a team that is not the org's (reports, spec, contracts) is kept as that team's record: a `FormerTeam` with `ended="not_taken"` under the nearest team of the org that holds its directory (`split.home_of_lost`), with a `not_taken` event in that team's record.
- **Shape.** Split, replace and prune work on a session's own places, approved by the place's Manager as before; `SessionInput.shape` is the tree shape the session started from. The tree's shape changes only through `Reviews._land` (`_put_team`).
- **Without review.** An opening place that changed nothing itself and meets nothing accepted meanwhile goes up without the reviewer (`_pass_up`, `Review.passed_up`); its review is `accepted` like any other.
- **What the human says in a session** is chosen among the session's own places (`choose_team(within=…)`), the teams it set up itself included. What the human asks anew is chosen among the tree's teams only.
- **Routing by where the human writes.** A new request (`route_message` with `auto`, `open_session` without a team) is chosen among the tree's teams. With `RouteMessageRequest.session_id` it continues that session: `_say_in_session` chooses among the session's places (`choose_team(within=…)`) and opens no session.
- **A request that is not a team's own** (`not_ours`) goes to the IC above inside a session. From the place a session was opened at, the session itself goes one team up the org (`Sessions._lift`, `OrgStore.lift_session`): the team above becomes the place it is opened at, in the same checkout, the old one a sub-team of it, and the Division Lead place moves up. The human is asked only from the top team, or when the session's work is in review already.
- **Two gates, one record.** `SessionTeam.merge` on the Division Lead place (`Merge`, made when the work is submitted, `_open_merge`) lists what waits as `MergeItem`s by `gate`: `ic` for code and specs, which the Division Lead IC settles with `review_team` before the merge, and `manager` for teams and contracts, which the Division Lead Manager settles with `settle_teams`. The two decide side by side and neither waits for the other. `Merge.seq` is its place in the order, `org_queued` says its teams and contracts wait behind an earlier session's (they are not worked out until it is first), `code_landed` that its code is in.
- **A reviewer that has to wait is told its turn.** Work is accepted in the order it was submitted, across sessions (`Reviews._before`). A reviewer refused because another session's reviewer has not decided yet gets the run-state mark `TURN` and is told once that work is decided on or its session closed (`_tell_turns`); it never has to ask again by itself.
- **Division Leads.** The two agents of a session's Division Lead place are the Division Lead IC and the Division Lead Manager (`SessionTeam.division_lead`, `is_division_lead`, `division_lead_id`, place ids ending in `@lead`, conversation titles). "Review" stays the word for the act, and "reviewer" for whichever IC reviews, an inner one included.
- **Spec and contracts say different things.** A spec covers only the inside of one team's folder; what teams promise each other is written only in contracts, and a spec does not repeat it (`ORG_PROTOCOL`, `WriteSpecTool`). So a spec lands with the code (Division Lead IC) and contracts with the teams they are true for (Division Lead Manager), and neither lead needs the other. The review request for a session's work shows the contracts the session wrote (`Reviews._contracts_written`), which its code is written to. Where the Manager does not take them (`Landed.others`), the session's IC is told the text that holds and to follow up on its merged code (`prompts.teams_settled`), and a `not_taken` event is landed for the folder's team (`_land_event`), also on close.
- **Work that is sent back joins the end of the line.** `_sent_back` drops the merge record and a resubmit gets a new number; holding a place for work that is being redone would block every session behind it. What the Division Lead Manager had decided is kept in the run-state mark `DECIDED` and seeds the next record (`_open_merge`), so it holds for whatever is unchanged (`_same`) and the Manager is not asked twice.
- **What waits for the Manager.** `Reviews._manager_items` works it out from the org as it is now, never from what was kept: `split.merge_shapes(base, theirs, now)` with base `SessionInput.shape` (a team the session left alone stays as the org has it, one only the session changed becomes the org's, one both changed or that would not hang together is an item), and contracts drafts the org changed meanwhile. A decision (`take`, `text`, `under`, `named`) is carried over for as long as what it was made of is unchanged (`_same`). A team is compared by the team above it, its directory, its name, what it may write and read, its agent profile and `since` (`split.made_of`). After the org part lands the base is the session's own shape, so a team the org keeps otherwise is not brought up again.
- **Who settles what waits.** The Manager of the Division Lead place is asked when the work is submitted and it is first in order, only if something conflicts, once for each state of it (`_ask_manager`, `Merge.asked`; `tell_manager(division_lead=True)`, `DIVISION_LEAD_MANAGER_ROLE`, `prompts.merge_request`). `settle_teams(teams, contracts)` only records: per team the org's or the session's (`TeamChoice`; a team taken from the session may be put under another team of the org, `under`, or called otherwise, `title`, checked by `_check_placement`: directory inside the other's, depth limit), per contracts the org's, the session's (the default) or a text (`ContractsChoice`). If what waits changed since the Manager was shown it, nothing is settled and it is shown again. Nothing is written until the code is accepted and it is its turn. A Manager that does not answer is asked again after `stall_check_minutes` and, once the code is merged, the human gets the escalation `ORG_WAITS` after as long again (`_check_managers`, from `_check_stalls`); answering it lands the org part with the org's standing wherever nothing was decided.
- **A team the org lost is never put back.** A session is not dropped when the tree no longer has a team of it. If the session changed nothing there the team stays gone. A team it set up under a lost one waits like any conflict, with `MergeItem.moved_to`: taken, it goes under the nearest team that holds its directory (or where the Manager puts it), that team's sub-teams inside its directory go under it, a `moved` event is kept, and the contracts the lost team set for it wait with it (a contracts item with `with_team`) to be added to the contracts of the team it goes under. A spec the session wrote for a lost team is shown to the Division Lead IC with the spec of the team that holds the directory now; unless the reviewer rewrites that spec in the same landing, the spec stays in its directory as an old spec of that team (`OrgNode.old_specs`), which the next session there is told to rewrite.
- **Closing.** Only the human closes a session; one whose work was accepted stays open so more can be asked in it. On close, a merge record whose code is in lands its org part with the org's standing wherever nothing was decided (`Reviews._settle_on_close`, in the base lane): what the session wrote lands where the org has the team and is a `not_taken` record where it has not. A record whose code was never accepted is dropped, and what the session wrote goes with it (`Records._leave`), named in the `session_closed` event, which is kept only if the org knows the session.
- **The reviewer merges.** Work whose files do not merge with the checkout above is not sent back. `Reviews._finish_merge` lays the merge out (`merge_checkout.prepare`: a detached worktree in `director-merging/` of the git directory, conflict markers left in; run-state mark `MERGING`) and tells the reviewer (`prompts.merge_prepared`). The reviewer edits only the listed files and runs no git there: `guard_action` refuses any other file, and on the next accept `merge_checkout.finish` refuses a changed file that merged by itself or a marker left in, stages the listed files, commits, and `merge_back.take_merge` fast-forwards the checkout above. It holds for inner places too. The team is told which files its reviewer finished. Files outside the team's directory still go back. Sending the work back or closing the session takes the laid-out merge away.
- **The reviewer writes specs.** `review_team(specs=[SpecChoice])`, for a session's work only: per directory of the work (or of a team that inherits a lost team's spec) the org's stays, the session's holds, or the reviewer's own text does (`Reviews.spec_choices`, applied to the session's drafts by `_take_spec_choices` right before they land).
- **Events, threads and routed requests are a session's own** until its work is accepted (`EVENTS`, `THREADS`, `ROUTED` marks; `Records.record_event`, `keep_routed`, `_keep_message`). Events and routed requests land with their team's part; threads never land, they reach the org only inside a removed team's record. Readers (`history_of`, `routed_requests`, `org_history`) show the org's plus the open sessions' own, the latter marked `TeamEvent.unaccepted`.
- **What is saved and exchanged.** What a session has is written to the run state as soon as it changes (`_keep_sessions`), not with the tree's delayed save. A fetch takes only `refs/agents/org` and `refs/agents/memory` (`org_sync.fetch`), a push gives only those; what a server keeps under `refs/agents` for itself is never exchanged. The lane orders one server; two servers on one repository are held apart only by the compare-and-swap underneath.

## Conversations the human reads

Every agent's conversation is an ordinary conversation of the server; one the director started itself is tagged `startedby=director` (`launch.STARTED_BY_DIRECTOR`), which a client leaves out of its list of chats. One the human writes in also gets `humanjoined=true` (`launch.HUMAN_JOINED`, `Delivery.joined`, the run-state mark `JOINED`), and is then listed with the human's own: `tell_ic(human=True)` does it for a message sent through the director and for the request a session is opened with, and a client that writes into an agent's conversation directly calls `POST /api/director/org/conversations/{id}/joined`. A session's conversations are titled with the session (`API · Refunds (IC)`). `GET /api/director/org/conversations/{id}` (`Records.place_of`) says where a conversation is (team, role, session) and links to the conversations one level away: the agents of the place above (for a session's opening place, its Division Leads), the other agent of its team, and the ICs of the places directly below (for a reviewer, the session's IC). A client uses the links to open one conversation inside another.

## Titles and headlines

Team titles and `headline`s come from one separate model call per team (`director/headline.py`, through `TeamLauncher.summarize`), never from the agents' own conversations, and a failed or slow call leaves the name the team has.

## Pruning

A Manager removes a team directly below its own with `prune_team`: `DirectorService._prune` stops and deletes the conversations of the team and of every team below it, discards the uncommitted changes in the team's directory after saving them as a commit under `refs/agents/pruned/<team id>/<time>` (`git.save_and_discard`), and removes the place, so the directory is the IC's above again; that IC is told the Manager's reason. A prune never starts a team, and it waits until no agent of the team or of a team below it is in a turn (`DirectorService._wait_until_quiet`).

## The agents' git

Every IC's terminal is started through a script in `<git dir>/director-shells/`, confined or not, because that script also puts the `git` from `director/git_index.py` first on `PATH` (through a bash `--rcfile`, since `~/.bashrc` may reorder `PATH`). Inside the org's repository that `git` runs the real one on `<git dir>/agent-index-<conversation id>`, where everything outside the team's directory is reset to `HEAD`, marked skip-worktree and ignored, so `git add -A` and `git commit -a` take only the team's own files; it resyncs when `HEAD` or the team's sub-teams change, runs HEAD-moving commands one at a time under `flock`, and after a commit resets the committed paths in the checkout's own index. Do not give agents a bare `GIT_INDEX_FILE`: an index that is one commit behind reverts that commit when it is committed from.

## Specs, contracts and ownership

A team is told its own boundary's `spec.md` and two sets of contracts, nothing else of the teams above: the spec (`Records.specs_of`), the `contracts.md` of its own boundary (between its sub-teams) and the `contracts.md` of the boundary of the team above (between it and the teams beside it) (`Records.contracts_of`), each as its session has it. The contracts of an approved split are written to `contracts.md`, not into the spec, so whatever a sub-team must respect has to be in them. `GET /api/director/org/nodes/{id}/ownership` (`director/ownership.py`) lists the files of a place's checkout by the direct report that owns them and the files that conflict when the tips of the checkouts of the place and its reports are merged in memory with `git merge-tree --write-tree`; uncommitted changes are not compared. For a tree team it lists the files of the repository's checkout by the sub-team that owns them and looks for no collisions (`collisions_checked` is false).

## Review

Work a team's IC submits with `submit_review` (refused while anything in its directory is uncommitted, or while its work already waits) ends that IC's turn and is reviewed by the IC of the team above, not by a separate agent and not by a Manager: `DirectorService._request_review` first asks the team's own IC two questions on top of its conversation with `TeamLauncher.ask_agent`, which records nothing in it: to write up what the team changed since `SessionTeam.base_commit` as a pull request description, and to review it with OpenHands' public `/codereview` skill as instructions (`director/bugbot.py`; `find_review_instructions` is injected so tests never load public skills). No diff is sent to a model; the questions carry only git's list of changed files. Both answers are stored on `SessionTeam.review` and sent to the IC above in a review request. Requests are held (the run-state mark `HELD`) so that the IC is woken once: `DirectorService._release_reviews` sends all of a place's held requests in one message when every sub-team has submitted or is `blocked`, at once when that IC is in a turn or starts one, and with an escalation an IC below raises; a paused org sends them on resume. A sub-team that neither submits nor blocks therefore holds back the reviews of the teams beside it until it is told to the IC above as stalled or is stopped (below). That IC decides with `review_team`. An accept merges the tip of a team with its own worktree into the checkout above (`director/merge_back.py`, under the lock the agents' `git` takes) and tells nobody further up unless the IC passed `needed_above`; work that conflicts or reaches outside the team's directory is sent back instead. A session's work goes into the human's own checkout only while that is on the branch the session was opened on (`SessionInput.branch`); on another branch, or with uncommitted work in the way, the human is asked with the escalation `MERGE_WAITS` (`Reviews._ask_to_clear`) and their answer merges it. There is no limit on rejections; `Review.round` counts them, and every `manager_check_ic_setbacks` of them on one piece of work wake the Manager above (`request_changes`), as that many escalations do. Each change is reviewed once, by the IC directly above the team that made it: after an accept, `DirectorService._pass_up` looks at the team above, and when all its sub-teams are accepted and it changed nothing itself (`_own_changes`: nothing committed since its `base_commit` or uncommitted in its directory outside its sub-teams') its work is merged into the checkout above and marked `accepted` with no review (`Review.passed_up`), and so on up. A team that did change something, and a session's opening place whose work meets what was accepted meanwhile, is left for its IC to `submit_review`; a merge that fails on the way up stops there and tells that team's IC. `DirectorService.settled()` waits for effects that effects queue, so a test can assert right after it.

## Memory sync and reports

The team memory leaves the machine only with the org, when it is pulled or pushed (`Sync._pull_memory`, below); there is no sync of team memory alone. `GitStore.merge` settles what both sides changed itself: reports become the union, and of any other file the local text is kept and named in `kept_local`. Either agent of a team records decisions, setbacks and reflections with `report`; they are kept per agent in `.reports/<team id>/<role>.json` of team memory, are only ever appended, and are read by the two agents of that team alone (`DirectorService.reports_of`), in `read_team_context` and in a briefing. Nothing is inherited down the tree and the human has no route to add one. When a report takes an agent's past `DirectorSettings.report_compaction_chars` characters (and a quarter of that is new since the last rewrite), a model rewrites them into one report marked `compacted` (`director/compaction.py`); the size is counted in characters because an external agent has no tokenizer at hand.

## Resting an IC

`submit_review` rests the IC: `DirectorService._rest` pauses its conversation after the step it is in (`TeamLauncher.pause`) and, in the lane of the team's messages, waits until it has stopped, so that nothing sent to it afterwards lies unread; the next message runs it again. An IC that runs its own tools is not paused, since that would end its process: the tool's answer tells it to end its turn, and one that still runs after `_REST_CHECKS` is cut short with `TeamLauncher.stop` (ACP `session/cancel`), which costs it the step it is in. Standing guidance from the human is a convention, not a feature: it goes into the repository's `AGENTS.md`, which every agent reads.

## Messages and proposals

An IC and a Manager talk in free text: `msg_manager` (an IC to its own Manager) and `msg_ic` (a Manager to its own IC, or with `team` to the IC of a team directly below). `Teams.message` keeps each message in the run-state mark `THREADS`, named `.threads/<manager place>/<ic place>.json` (`records.thread_name`), and delivers it through the outbox; the threads are the session's own and never land in team memory, except in the record of a team that is removed; `GET /api/director/org/nodes/{id}/messages` returns the threads a place's agents take part in (`threads_of`). An IC proposes sub-teams with `propose_teams` (`teams` with `name`, `path`, `instruction` and optional `reason`, `model`, `writable`, `readonly`, `isolation`, plus `contracts`, `keep` and `text`); the tool's schema refuses what is not a proposal, and the Manager reads the proposal as a message of the thread (`split.as_written`). A team without sub-teams has no use for `msg_manager` and is refused it. A proposal that fails any check (`split.normalize_split`, `check_limits`, the allowed profiles) is refused to the IC and nothing reaches the Manager; one that passes is kept in `SessionTeam.pending_split`. The Manager sets the teams up exactly as written with `approve_teams`; any `msg_ic` to its own IC while a proposal waits puts it aside, and a later proposal replaces an earlier one. There is no count of attempts. An IC never configures a Manager: every team gets one, derived from its IC.

## Replacing teams

Proposed teams may overlap the ones the team already has: a team whose directory equals, holds or lies inside an existing direct sub-team's replaces that sub-team (`SplitProposal.replaces`), and whatever the new teams leave of the directory is the proposing IC's again. An IC that already has sub-teams must say what becomes of each: the proposal's `keep` lists, by name or team id, every sub-team that stays as it is (`SplitProposal.keeps`), and `split.normalize_split` refuses a block that leaves a sub-team neither kept nor replaced, keeps one it also replaces, or names one the team does not have. Only a proposal's first check asks for `keep`; the checks at approval and at set-up pass none. A proposal never removes a team without replacing it: that is the Manager's `prune_team`. A replaced team's own sub-teams stay and are moved with `OrgStore.move_place` (which re-routes their escalations) under the new team that holds their directory, else under the proposer; a proposed team may not sit inside such a sub-team, and a team with a worktree of its own cannot be replaced while sub-teams work in that worktree. `DirectorService._carry_out_split` fixes the whole plan in the intent's first step, waits until the replaced teams and their sub-teams are at rest (messages to them stay in the outbox meanwhile), merges what replaced teams committed in their own worktrees into the proposer's checkout (`_take_in`; a conflict declines the approval and changes nothing), saves their uncommitted work under `refs/agents/pruned/`, removes them and sets the new teams up.

## Starting teams

Setting teams up starts nothing: a new team has no agents (`SessionTeam.agents` is empty) and its `instruction` is kept as what it is for (the run-state mark `TASK`). Its IC is added and started by the first thing sent to it (`DirectorService.tell_ic`: a `msg_team` from the IC above, a message from the human, a review request for a sub-team moved under it), with that message as the end of its briefing; send to an IC through `tell_ic`, never by looking its conversation up. A team that was never started owes nothing: it cannot stall, holds back no review of its siblings and does not keep the team above from going up (`_may_stall`, `_release_reviews`, `_pass_up`). An agent is derived from the nearest IC at or above its team that has started (`_started_ic`). Teams waited for are kept in memory only (`_settling`) and found again when the step is carried out again. A Manager is woken by its briefing, a `msg_manager`, an escalation from below, a team its IC stopped and the two checks below; nothing wakes it when a sub-team is `blocked` or when approved teams cannot be set up: its look says how long a blocked team's IC has waited, and a set-up the runtime refused is kept in the record as `declined` (`_decline`), where it reads it.

## What a removed team leaves

A team that is removed, by a proposal that replaces it or by `prune_team`, leaves nothing a later team finds by accident (`DirectorService._archive`, called before `store.remove`): it makes one record (`FormerTeam`: title, directory, purpose, how it ended, its review, its reports in full and as one report a model shortened, the contracts between its sub-teams, its message threads), takes its threads out of the session's run state (`Records._take_threads`) and drafts the removal of its `contracts.md`; the run-state marks `TASK`, `PROGRESS`, `CHECKS` and `REPORTS` of its place are cleared. The record is the session's own (`FORMER`) until its work is accepted; then it is written to `.former/<team id>/<time>.json`, and the team's reports and record of its sub-teams are deleted in the same commit if the org no longer has that team (`Landing.forget`). If the org kept the team, the record lands as `not_taken`. This matters because a team id comes from the directory, so a new team in the same directory has the old team's id; until the accept, `Records.is_orgs` keeps the new team from reading the old team's reports. Recording a removal again changes nothing, which is what makes the step safe to carry out twice. Only `spec.md` stays where it is: a new team is marked with the specs it finds in its directory (`OrgNode.old_specs`, set in `_specs_left_in` for a team's own directory and for the directories of replaced teams that hold it or lie in it; after a prune, on the team above), `DirectorService.specs_of` returns them with `old` and `left_by`, briefings and the context (`specs_left_by_teams_before_you`) say they are old, and `write_spec` clears the mark. Reports belong to an agent of a team, not to a conversation: `.reports/<team id>/<role>.json`. Sub-teams of a replaced team that was stopped go on under the team they are moved to (`_go_on(own_too=True)`), with their time without progress started again.

## Managers and their looks

A started team has its IC alone. Its Manager is added to `SessionTeam.agents` and started by the first thing sent to it (`DirectorService.tell_manager`: a `msg_manager` or an escalation a Manager below raised), briefed with the team's task from the run-state mark `TASK`, so send to a Manager only through `tell_manager`. The director also wakes a Manager to look at its teams on two counts kept apart in the run-state mark `CHECKS` (`DirectorService.count_accepted_review`, `count_ic_escalation`): every `DirectorSettings.manager_check_accepted_reviews` (default 5) reviews its IC accepted with `review_team` (work that went up by itself in `_pass_up` is not counted), and every `manager_check_ic_setbacks` (default 3) escalations that the IC of one team directly below raised or passed up to its IC on the work that team has in hand. Each count starts again when it wakes the Manager and neither touches the other; a team's escalation count also starts again when its work is accepted (`_work_accepted`), since what it does next is other work, so the count belongs to a team and a piece of work, not to a team for good. 0 turns a check off. The wake-up (`prompts.manager_check`) lists the teams below with their status, review, escalations and time without progress, and asks for nothing.

## Stalls and stopping

What a session uses is counted, and its cost can be limited. With every look of the stall watch `Watch._count_use` reads what each conversation of a session has used (`TeamLauncher.usage`) and adds what is new since the last look to `SessionInput.usage` (the run-state mark `USE` keeps the last reading of each conversation, so a count that begins again with a server takes nothing away). A conversation's use is read per model it ran on (`launch._used`): an agent that runs its own model (an `ACPAgent`) reports its cost itself, and what it read from and wrote to its cache apart from its input, which is added to the input because it is nearly all of it; another agent's cost is what the SDK recorded with LiteLLM's prices and, where that is nothing (a model behind a gateway or under a name of its own), what `pricing.priced` derives from LiteLLM's public price list for the model its name ends in, cache reads and writes at their own price. Tokens no price is found for are counted in `Usage.unpriced_tokens` and are in no cost, so no limit holds them; the page says so. The director's own model calls on an agent's model are counted the same way and added. `DirectorSettings.session_cost_limit` (US dollars; 0: none) is what a session may cost; `SessionInput.cost_allowance` is where it is held next. A session that reaches it is put to rest the way a stopped team is (`Stopped` on the place it was opened at, so everything sent to its agents waits) and the human is asked with the escalation `LIMIT_WAITS`; their answer lets it go on for as much again (`Watch.go_on_past_limit`) and is sent to its IC. What a team uses stays no measure of the team: it limits a session and is told to no agent. `DirectorSettings.max_open_sessions` (0: no limit) refuses one session more in `open_session`. A team started from a profile spends under the caps of the agent it is started for (`max_iterations`, `max_budget_per_run`), as a derived agent does.

Teams that get nowhere are found by time, not by counting rejections. The director keeps when each team last got anywhere in the run-state mark `PROGRESS` (`DirectorService.progressed`: its start, a `submit_review`, a review decision, an escalation raised or settled, an accept of one of its sub-teams, a `msg_team` to it; and a new commit under its directory, which `_check_stalls` finds with `git.last_commit_in`). Every `STALL_POLL_SECONDS` `_check_stalls` looks at each team that owes work nobody is waiting to give it (`_may_stall`: not submitted, or sent back; not `blocked`, not under a stopped team) and, after `DirectorSettings.stall_check_minutes` (default 120, 0 turns it off) without progress, tells the IC above once (the human, with the escalation `STALL_WAITS`, where no IC works above: `Teams.tell_above`), and once more for each further such stretch: `prompts.stall_notice` carries how long, what the team's own IC answers when asked on top of its conversation (`STALL_QUESTION` through `ask_agent`; not asked while it is in a turn) and the git commands to look for itself, and the reviews held for that IC are released with it. The first notice about a team counts as progress of the team above, so that IC has one stretch to act before it is told on itself. The clocks start again when an org is resumed and when a server starts; the clock is injected (`clock`, `stall_poll`) and tests call `_check_stalls` themselves. An IC writes to the IC of a team directly below with `msg_team` (`DirectorService.message_team`, kept with the session in the run-state mark `THREADS` and returned by `threads_of` as a `Thread` with `ic_to_ic`); nothing goes back up that way, the team answers through its work or an escalation. As a last resort an IC stops a team directly below with `stop_team`: `SessionTeam.stopped` (set with `OrgStore.set_stopped`, which makes the status `blocked`) records why and which conversations were in a turn, the agents of the team and of every team below it are paused, `_deliver` holds everything sent to them in the outbox (the human's words too), and the Manager of the stopping IC's team is told. A stopped team goes on when that IC writes to it with `msg_team` (`_go_on` delivers what waited in the order it was sent and runs the agents that were cut off), can be replaced through a proposal (`propose_teams`) and can be pruned by the Manager like any other team; the human has no control to stop one.

## Context

An agent is told its team's context without asking. `DirectorService.context_of` builds it (it is also what `read_team_context` returns), a briefing ends with the parts it does not already say in its own words (`context.briefing_block`), and what the agent was told is kept per conversation in the run-state mark `TOLD`. A change to the context never sends a message, since every message starts a turn: `_deliver` compares the context with what was told (`_with_what_changed`) and appends a `[director] context update` block to whatever message goes to that agent next, the human's included. `context.steady` leaves out what comes and goes with every turn (`working`/`idle`, headlines), a list that only grew is told as what was added, the list of sub-teams is told as the teams that changed or went (`context._entries_changed`), and an agent is not told back its own reports or the escalations it raised. An update stays small: it never carries what the agent wrote itself (`Delivery.knows` takes its own `spec` and `pending_split` as told; an IC is not told its own `status`), the review entry is state and round only, a proposal is its status and team names outside `read_team_context`, lists known by an id (`context._KEYED`) are told as added, changed and removed, one text is cut at `context.CUT` characters, and a briefing leaves out empty fields. A system prompt cannot carry this: it is fixed when a conversation starts and derived agents inherit their parent's. Add a field to the context in `context_of` and it reaches briefings, updates and the tool alike. A model call the director makes for itself, apart from any conversation, goes through `TeamLauncher.ask` with its own `usage_id`.

## Unfinished work and recovery

The director's unfinished work is kept outside git history, in the SQLite file `<git common dir>/director/state.db` (`director/run_state.py`): which agents were running, which teams wait for a run slot and in what order, the multi-step actions it began (intents) and the messages it has not delivered. A multi-step action goes through `DirectorService._begin`, which records it before its first step; `_carry_out` runs the `_do_<kind>` handler, which marks each finished step with `run.step_done` and skips marked steps, so every handler must be safe to run again. Messages to agents go through `_post`/`_send` (held, then delivered: at least once). `POST /api/director/org/pause` and `/resume` stop and continue all of it, `GET /org/recovery` says what a resume will do; a server that starts with unfinished work loads the org paused (`shutdown` or `crash`) unless `DirectorSettings.resume_on_start` is set. `director/recovery.py` drops run state that no longer fits the sessions (another server's file, a step of a place that is gone or whose split or review no longer stands, a message to an agent that is gone) and names what it dropped. Finished intents and delivered messages are deleted, so the file holds only what is open. An agent a restart cut off is told to carry on (`_run_again`) and shows paused until it is seen running (`_resuming`): until then its conversation still says the error the restart left, which is not a failure of its own.

## Inheritance, hand-over and the record

What a team inherits from the teams before it is decided, so keep to it: nothing by itself. A team is cleared, split or merged only through a proposal (`propose_teams`) and removed through `prune_team`; there is no merge or re-parent command, and a clear is simply a different team proposed for the same directory. What the removed teams left is given to the IC that proposed the change, or to the IC above a prune, in hand-over mode: a side conversation of that IC which the director starts for that hand-over alone (`DirectorService._do_hand_over`; it is no agent of its own but `AgentRef.hand_over` on the team's IC, found by `OrgStore.find_hand_over`, derived from the IC's conversation and briefed by `prompts.hand_over_brief` with each team's reports as one report, in full, the contracts between its sub-teams, its spec, who has its directory now, and the team's own context). It shares nothing with the IC's main conversation, which is only told that it runs and, when it ends, what it did (`handed_over_notice`); its status does not count toward the team's, it edits no files, and of the director's tools only `read_team_context`, `hand_over` and `write_spec` work in it. Each hand-over gets a new one, which replaces the one before; where it cannot be started it is tried once more, and then the mode stays on the IC with the status `lost` and the IC's main conversation is told so and nothing more, by decision: the job is not moved there. A hand-over conversation is paused, run again and read back after a restart as an agent's own is (`recovery.put_aside_stale` keeps its marks, `_resync_hand_overs` ends one that finished or was lost meanwhile). That IC decides which team gets what with the `hand_over` tool (`DirectorService.hand_over`: notes are kept with the team's IC reports as a `Report` with `handed_over`, which a briefing and the context show as written by the IC above; contracts replace the team's own `contracts.md`; both are the session's own until its work is accepted). `hand_over` starts nothing, nothing waits on it, and it can be repeated; `read_team_context` returns the records again for an IC (`former_teams`, in full only from the tool; the context told with every message only names them). The hand-over conversation is told to rewrite the team's spec, and the answers of `approve_teams` and `prune_team` tell the Manager it may need to explain the change with `msg_ic`. The `contracts` of a proposal that replaces teams take the place of the team's `contracts.md`; a proposal that replaces none adds to it. What became of the teams directly below a team is kept in team memory as `TeamEvent`s (`.history/<team id>.json`, written when the session's work is accepted; until then `DirectorService.record_event` keeps them with the session: set up, accepted, sent back, stalled, stopped, replaced, pruned, and each time the Manager was woken with the reason). It outlives the teams it is about; a team's own file goes with it when it is removed. Both agents read it through `read_team_context` (`track_record_of_the_teams_below`), a review request carries the team's record, and `manager_check` lists it, with the teams that are gone. It is not part of the context told with every message, so it adds no context update. A team that was set up and given no task for `stall_check_minutes` is told to the IC above once and not again, since a team may wait on purpose (`prompts.unstarted_notice`, from `_check_stalls`); it is not a stall and is not recorded as one. The memory route returns the removed teams and the record for a client (`NodeMemory.former_teams`, `NodeMemory.history`). `GET /api/director/org/history` returns the records of all teams as one list, newest first (`DirectorService.org_history`, without the `needed` events). How teams are split, merged and pruned is decided, so keep to it. An IC splits by concern first (one thing a team can own behind a short contract) and for efficiency; teams working at the same time follow from that and are not a reason to split (`ORG_PROTOCOL`). A proposed team and the block may carry an optional `reason` (`SplitChild.reason`, `SplitProposal.reason`). The director adds to a proposal, for the Manager, what it knows (`DirectorService.facts_of_proposal`, `prompts.proposal_facts`): files in each directory, commits that changed two proposed directories together, and teams that had a directory before with why they were pruned. Proposals and approvals are kept in the record (`proposed`, `approved`). A Manager declines what its IC proposed with `decline_teams` and a reason (`agent_actions.decline_teams`), which is kept as `declined` with the proposal's directories (`TeamEvent.paths`) and told with a later proposal for the same directories; a message with `msg_ic` decides nothing, and what was proposed waits on the Manager until it approves or declines or the IC proposes again. A Manager is woken only by the two counts it had (accepted reviews, and one team's escalations on the work in hand); work that is sent back is recorded, and wakes the Manager once it was sent back as often as that number. When the escalation limit is reached the `woken` event names the team, and `track_records` counts for each team its tasks and the ones on which that limit was never reached; `manager_check` tells the Manager that as the team's success rate (`success_rate`, with `success_rate_meaning` naming the number from the one setting `manager_check_ic_setbacks`). Token use is deliberately not a measure of a team: tasks differ in difficulty. A Manager may prune any team directly below; the runtime refuses none on its record, by decision. It is told to prune only a grossly inefficient team, that it is never obliged to, and to wait until a team has had enough tasks to judge it by; how many is its judgment and deliberately no setting. What says that two teams should be one is counted, not guessed: a write by one team's IC that the runtime refused because the file is a sibling's (`guard_action`), and a review finding on one team's work that names a sibling's file (`request_changes`), are kept as `needed` events with the other team (`DirectorService.record_need`, `TeamEvent.other_id`, the same file and way once, which is looked up in the record itself and so holds across restarts). `prompts.needs_between` counts them for each pair of teams that are there, from the time each was set up. From `NEEDED_WORTH_SAYING` (3, deliberately no setting) the IC is told in a review request for either team and by `read_team_context` (`teams_below_that_needed_each_other`); a Manager is told any count when a proposal replaces both teams. It wakes nobody, merges nothing, and is by decision not part of a Manager's look. Escalations that merely name another team are not counted: a text match can be wrong. The human still cannot prune, replace or split.

## Exchanging an org with a remote

An org is exchanged with a remote of its repository only when asked, as git does a branch: `POST /api/director/org/push` and `/org/pull` (`director/org_sync.py`) move `refs/agents/org` and `refs/agents/memory`, nothing else: sessions, with their agents, checkouts and branches, stay on the machine that has them. A pull is a merge (`director/org_merge.py`, a pure function over saved teams): a team or a field changed on one side only is taken from that side; the same field changed on both, a team removed on one side and changed on the other, and a spec or contracts both rewrote in the same lines are conflicts. With conflicts nothing is written, the org stays paused, the merge is kept in the run state and `GET /org/merge`, `POST /org/merge/resolve` and `/org/merge/abort` settle it; finishing writes a commit with both parents. A saved team has only what `OrgNodeInput` has, so nothing of a machine's work is merged, and a pull leaves the open sessions as they are (`Sync._apply`). A clone that pulled an org has its teams and no agents: work begins there with a request, which opens a session. An agent of a session whose conversation is not on the server is `lost`, and `POST /org/sessions/{session id}/teams/{team id}/start_again` starts that place afresh in its own checkout. Without a conversation `start-again` starts the place's IC like the IC above it in the session, or failing that like the IC another session started with (or from the team's own agent profile). `tree-stream` carries `paused` and `merging` in its snapshot and an `org_state` event on every change. When teams change place (`OrgStore.move`, a tree read again, a pull) every subscriber is sent its snapshot anew (`OrgStore.show_again`) and starts over from it. The intents `accept` and `request_review` are forgotten only after the tree they changed is saved, so a server that ends in between does them again; an `accept` found already accepted still does what follows it (`_pass_up`).

## The human's edits

The human reads and changes a team's files through `director/changes.py`: `GET /api/director/org/nodes/{id}/changes` lists what differs in the team's directory from `SessionTeam.base_commit` (uncommitted and new files included), `.../changes/file?path=` gives both sides of one file, and `PUT .../files?path=` writes one file, commits it alone as `Edited by hand: <path>` and tells the team's IC, which starts a turn of it. The write is held to what the team's own agents may write (`changes.edit_refusal`, the same rules as `boundary.write_refusal` worded for a person) and is refused with 409 while an agent of the team is running. All three take the id of a place; a tree team has no checkout and answers 404. There is no shell for the human.

What an accept took can be read after its session is closed: an `accepted` event keeps the two commits (`TeamEvent.base`, `head`) and the team's directory (`paths`), and `GET /api/director/org/accepted/changes?base=&head=&path=` and `.../changes/file` read them from the repository (`accepted_changes`, `accepted_file`). Only commit ids are passed to git. The commits are in the repository as long as the work was landed; a session closed before that can lose them, which is a 404.

## ACP processes

An `ACPAgent`'s command is started in a session of its own (`start_new_session`), and closing the agent signals the whole process group, then kills what is left of it after `_ACP_GROUP_EXIT_GRACE_SECONDS`: the command is usually `npx`, which starts `node`, which starts the agent. Test stand-ins for the process set `pid = None` so that closing has no group to signal. The director's `sandbox.command_script` adds bubblewrap's `--die-with-parent` for an agent's whole process, not for a terminal's shell (`shell_script`): the kernel counts the thread that started a process as its parent. A message to an ACP agent in the middle of a turn ends that turn, so `DirectorService._deliver` leaves the director's own notices in the outbox while such an agent runs and `_note_running` delivers them when its turn ends, joined into one message (`_deliver_what_waited`), since each of several would end the turn the one before began; only what the human said (`route_message`, `answer_escalation`) is posted with `at_once=True`. The intent `finish_split` is saved before it is forgotten, like `accept`.
