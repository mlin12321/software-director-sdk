# The director

See the [project root AGENTS.md](../../../../AGENTS.md) for repository-wide policies.

The director keeps an org tree of agent teams and a team memory, and runs the teams' agents, an IC and a Manager each, in sessions. It is code with fixed rules, not an agent. What follows is decided; keep to it when changing the module.

## The director holds services

`DirectorService` (`director/service/__init__.py`) is one class with no base. Everything it does is done by a service it holds and is called as `service.<name>.<method>(...)`: the org is `service.org_load.org`, a session is opened with `service.session_lifecycle.open_session(...)`. There are no mixins and no forwarding methods: do not add a method to `DirectorService` for what a service can do.

**What `DirectorService` keeps.** Its constructor takes the server's configuration and builds the coding environment and the services that need nothing of the others; `_build_services` builds the rest; `__init__` registers the steps of resumable work. Besides that it has only what belongs to the server's lifetime: `start` and `aclose` (the timer task, and beginning and ending `agent_launch`), `from_config`, and `is_agent`, which the server's conversation routes call. The module also has `lane_for`, `SAVED_BEFORE_FORGOTTEN` and the default timings.

**A service** is shaped as the agent server's own are (`BashEventService`, `EventService`): a `@dataclass` named `...Service` in `service/..._service.py`; what it is given as public fields (other services, or functions that return a thing as it is when asked, such as `org: Callable[[], OrgStore]`); what it keeps for itself as `field(init=False)`; `__aenter__`/`__aexit__` only if it owns tasks. It imports only other `..._service` modules of `director.service` and is never given `DirectorService` (`test_director_layering.py`), so it is tested with what it is given.

**Order.** `_build_services` builds each service after the ones it is given, as plain attributes, and gives it the services themselves. A function that asks for a service built later (a `lambda` in the builder that names one) is the exception, and there are six, in two kinds. Loading the org lazily ties four services in a knot: `org_state` asks `org_load` which repository the org is in, and `org_load` asks `team_types` for a team's type, tells `org_save` that the tree changed and tells the director that the org was loaded. Two services call up to what is built on them: `message_delivery` takes a step up through `resumable_work` when a team's agents come to rest, and `team_messaging` releases reviews through `reviews`. Do not add a seventh: when a service needs something of one built after it, the method is in the wrong service. Move it down (as `progressed` went to `OrgStateService`, `review_instructions` to `TeamTypeService`, `derived_from` to `OrgStore`), or have the caller above both do the second half (as `SessionLifecycleService.not_ours` asks `RequestRoutingService.take_back` and then hands the request on itself).

**What a service is given once.** A service is not given the same thing twice: one that holds `org_settings` asks it for `team_documents()`, one that holds `org_state` asks it for the clock, one that holds `message_delivery` marks a conversation joined through it. A service that needs more of the org than its tree (where it lives, which server runs it) is given `org_load`; one that only reads the tree is given `org` as a function, which is what a test hands it. A service that needs more of the launcher than the launcher (the loop, whether agents run) is given `agent_launch`; the others are given `launcher` as a function.

**A new step of resumable work** is a payload in `intents.py`, a `do_<kind>` method on the service that carries it out, and one line in the table in `DirectorService.__init__`.

## What the director changes in OpenHands

The director is new files (`director/`, `director_router.py`, `tests/agent_server/director/`, `tests/sdk/agent/test_acp_agent_director.py`), which never conflict when upstream is merged. What conflicts is a change to a file OpenHands has, so there are few, and `test_director_layering.py` fails when a file joins them (`CHANGED_IN_OPENHANDS`). Put a new test of the director in its own files, never in a test file of OpenHands. Before adding a hook to an OpenHands class, look for a way from outside: `not_an_agent_of_the_org` refuses three conversation routes as a dependency given where `api.py` mounts them, and `conversation_router.py` is as OpenHands has it.

| File | What is changed | Why not from outside |
|---|---|---|
| `api.py`, `init_router.py`, `config.py`, `dependencies.py`, `server_context.py`, `__main__.py` | The director is made, started, stopped, mounted and configured with the server. | This is where the server is assembled. OpenHands rarely changes these lines. |
| `conversation_service.py` | `add_execution_status_listener`, `add_action_guard`, `add_resume_adapter`, `get_execution_statuses`, `loaded_event_service`; `server_tools`, `tool_params`, `adapt_agent` on `start_conversation`; `child_id`, `worktree_options`, `tool_params`, `extra_tags`, `confirmation_policy`, `adapt_agent`, `workspace_dir` on `start_child_conversation`; a worktree from a commit that is here fetches nothing. | A conversation the server loads again (after a restart, or when it was idle) gets a new `EventService`, which only `ConversationService` makes: a listener or guard put on from outside would be lost then. The agent is resolved in the middle of `_create_conversation`, so tools and the adapter can only be given there. A child started through `start_conversation` instead would be launched as a new conversation is (settings, experimental tools and memory applied again) and could not keep its parent with a directory of its own. |

| `sdk/agent/base.py`, `sdk/conversation/impl/local_conversation.py`, `sdk/agent/acp_agent.py` | `ask_aside`; the fork of `ask_agent` asked on the conversation's model, given up after a timeout, and refused plainly by a server that cannot fork; a launcher in front of `npx`; Cursor's login file; the command started in the workspace directory. | They are inside the ACP agent's own connection and process. |

## The coding environment

Everything the director does with git goes through one `CodingEnvironment` (`director/environment/`), which `DirectorService.__init__` builds once as `self.environment`. It has four parts, each said without git:

- **`Checkouts`** (`environment/checkouts.py`, handed on as `self.checkouts`): the state of a team's work (`version`, `branch`, `uncommitted`, `astray`, `own_changes`, `changes_listed`), two teams compared (`is_apart`, `overlap`), work moved (`merge`, `lay_out_merge`, `finish_merge`, `take_merge`, `undo_merge`, `set_aside`, `bring_over`, `keep_unmerged`), checkouts that are gone (`missing`, `restore`), and what the human reads and edits by hand (`team_changes`, `file_sides`, `write_by_hand`). Its value types are `MergeBack`, `MergeCheckout`, `Overlap` and `Unfinished`.
- **`RecordStore`** (`environment/records.py`): one store of an org's records, which takes each change whole or not at all. What keeps a store implements twelve things (`head`, `read_at`, `files`, `stage`, `commit`, `land`, `clashes`, `merge`, `move_to`, `contains`, `base_with`, and its `name`); how team memory is laid out in one (`write`, `reports`, `replace_reports`, `former`, `former_below`, `history`, `routed`, `take_in`) is written once on the base class over those, and `test_record_store.py` runs it on a store kept in memory. A store's `merge` still has to settle a file both sides changed with `records.settle`. `environment.team_memory(repository)` and `environment.org_tree(repository)` give the two an org has; `environment.land_together` moves both at once or neither. The same module has how team memory is laid out in a store (`Landing`, `taking_in`, `normalize_store_path`, `team_key`, `reports_file`), whatever keeps it.
- **`Remote`** (`environment/remote.py`, `environment.remote`): `fetch`, `push`, `behind`, and what was fetched of the other side's two stores.
- **`Confinement`** (`environment/confinement.py`, from `environment.confinement(repository, ...)`): what holds the agents of a repository to their scopes: `confine` (the shell an agent's terminal starts), `adapter` and `with_tools_again` (the tools its agent is given), `check` (an action of a file tool) and `forget`. `AgentConfinementService` asks for one as the server is now and decides the scopes.

`environment/git/` is the one implementation and the only place git is run: `GitCodingEnvironment`, `GitCheckouts` (`checkouts.py`), `GitStore` (`git_store.py`, a hidden ref changed by compare-and-swap), `GitRemote` and `GitConfinement` (`confinement.py`: bubblewrap, and the agents' own `git` from `git_index.py`), over `cli.py` (one git command; `GitError`), `merge_back.py`, `merge_checkout.py`, `reconcile.py`, `ownership.py`, `changes.py`, `org_sync.py` and `git_index.py`. `GitError` is an `EnvironmentFailed`, and that is the name callers catch.

`environment/memory/` keeps the records and the remote in memory and runs no git: `MemoryRecordStore` (a store of a `MemoryRepository`, whose versions know the versions they were made from), `MemoryRemote` (a remote is another repository of the same `MemoryRecords`), and `MemoryRecordsEnvironment`, which pairs them with another environment's checkouts and confinement. It is for tests, and it is what holds the two interfaces to what they say: `test_record_store_contract.py` and `test_remote_contract.py` run the same tests against git and against memory, so **a change to `RecordStore` or `Remote` is made in both and tested in both**. The one difference is said in `MemoryRecordStore`: it merges files whole (`records.merge_files`), where git first merges the lines only one side changed. There are no checkouts in memory.

**Nothing outside `environment/git/` imports from it**, except `service/__init__.py`, which builds the environment (`test_director_layering.py` checks it). A service that needs a team's checkout takes `checkouts: Checkouts` as a field; one that needs the stores takes `environment: CodingEnvironment` or a function that gives a `RecordStore`. Sentences that explain a git state to an agent are returned by the environment, not written where they are sent from. The git environment keeps no state: what must survive a restart (a laid-out merge, for one) is kept by whoever asked, in the run state.

What this does not make swappable: the upstream conversation service makes the worktrees when the launcher starts an agent with `isolation="worktree"`; the saved model keeps `worktree_path`, `branch`, `base_commit` and `Review.commit`; the prompts say "commit" and "checkout"; and the agents' own `git` (`environment/git/confinement.py` and `git_index.py`) is git whatever the interface says: an agent runs `git` in its shell.

## Org tree and team memory

The director (`openhands-agent-server/openhands/agent_server/director/`, routes in `director_router.py` under `/api/director`) keeps an org tree of agent teams and a team memory in hidden git refs (`refs/agents/org`, `refs/agents/memory`) of the org's repository. That is the git repository of the workspace of the org's first conversation, wherever the server was started: `SessionLifecycleService.create_org` moves the org there (`OrgLoadService.move_to`) and writes it to `director.json` beside `Config.conversations_path`, which is read first on the next start. Until there is an org, the director looks in `Config.director_repo_path` (default `workspace_path`). A repository that has no org and is a git submodule stands for the nearest repository above it that has one (`DirectorService._load_from`), both at startup and when a first message arrives; `OrgSummary.repo_path` is the org's repository and `OrgSummary.directory` is where the server's own directory sits in it, which is where a message without a `path` is routed from. Tests that start an org through the app must point `conversations_path` at a temporary directory, or `director.json` leaks between them. `GitStore` never touches the working tree or the user's index: it builds trees in a throwaway `GIT_INDEX_FILE` and lands them with a compare-and-swap `git update-ref`, retrying when another writer wins. `OrgStore` owns the derived `child_ids` and is the only emitter of org events; mutate the tree and the sessions through it. A stream subscriber follows one focus team plus the teams it has expanded (or the whole subtree with `full`), and gets the open sessions and the list of escalations that wait on the human, of every session whatever its focus, whenever either changes.

## Escalations

An escalation is raised at a place of a session and goes up inside that session: it is held by the place above the one that raised it and moves only through `OrgStore.pass_up_escalation`, one place at a time with a reason, so `held_by` is `None` only after every place above has passed it up (the store rejects anything else). The chain ends at the place the session was opened at (`OrgStore._chain` stops at the Division Lead place), so what that place raises or passes up waits on the human. Keep it that way when adding ways to raise or route escalations. Escalations run in two lines: `Escalation.raised_by` is the role of the agent that raised it, and at each place it is that role's agent that is told (`TeamMessagingService.hand_escalation`) and that may settle or pass it up with `resolve_escalation`, so an IC's goes IC to IC and a Manager's Manager to Manager; the human's answer goes to the agent that raised it. The wire types are mirrored by hand in `clients/typescript/src/models/director.ts` (client-ahead of the pinned release); change both together. `DirectorService` loads nothing until first use, so `create_app` stays free of git calls.

## Agents are conversations

An org's agents are ordinary conversations: `POST /api/director/org` starts the IC of the org's first session from the caller's `StartConversationRequest`, as does any request that comes with a conversation, and every other agent is derived from an existing one with `ConversationService.start_child_conversation` (a Manager from its team's IC, a sub-team's IC from the IC above, a session's IC or Division Lead IC from an IC that runs already: `TeamMemberStartService.derived_from`, `TeamMemberStartService.template`), so model configuration and secrets stay in the conversation store and never reach the org ref. The director reaches conversations only through `TeamLauncher` (`director/launch.py`), which tests replace with a fake.

## Agents that run their own tools

An agent that runs its own tools (an `ACPAgent`: Claude Code, Codex) can be any agent of an org, the IC a session starts with included. It cannot be given the director's tools in-process and its tool calls never pass `guard_action`, so `AgentConfinementService.adapter` changes it as its conversation starts (the `adapt_agent` hook of `start_conversation` and `start_child_conversation`): `mcp_config` gains the stdio MCP server `director/mcp_shim.py` (standard library only, run by its path), which lists the tools from `GET /api/director/tools` and passes each call to `POST /api/director/tools/{name}`, and `acp_command` is prefixed with `<git dir>/director-shells/<conversation id>.acp.sh` (`sandbox.command_script`), which starts the agent's whole process in the team's sandbox with the team's `git` first on `PATH`. The token reaches the shim in its environment, a secret, and a server without `OH_SECRET_KEY` does not keep secrets between runs: when a conversation is loaded again its saved agent passes through `AgentConfinementService.with_tools_again` (`ConversationService.add_resume_adapter`, applied in `EventService` after the saved agent is read and before it starts), which makes the tools server again from the director's own key. Those two routes are mounted outside the session-key dependency: the caller is known only by `X-Director-Agent-Token`, an HMAC of its conversation id (`director/acp.py`) with a key kept in `director.json`, so it survives restarts and never reaches the org ref. They run the same `agent_actions` as the in-process tools (`director/tools/remote.py`); what a tool takes and does is said once, as a `ToolSpec` in `director/tools/catalog.py`, which knows nothing of the agent SDK; `director/tools/definition.py` is the one module that makes the SDK's actions and tools of those. To add a tool, write its `ToolSpec`, give it its action and tool class in `definition.py` (`DIRECTOR_TOOLS`), name it in `DIRECTOR_TOOL_NAMES`, and give it to the member that may use it in each type under `director/orgs`, and both ways get it. Which tools an agent has is `TeamTypeService.tools_for(place, member)`: the `tools` its team's type gives that member, or at a Division Lead place its `lead_tools`. A tool's free text is named `text` in every tool; name a new tool's the same. An agent is offered only those tools: `AgentConfinementService.adapter` puts them in place of the ones a derived agent carries from the agent it was derived from (a Manager from its IC), `GET /api/director/tools` lists them for the caller, and `tools.remote.call_tool` refuses a call of a tool the caller is not offered; `agent_actions._has` stays the check that the caller's member has the tool. What an agent always reads is kept short, so keep to it: `ORG_PROTOCOL` holds what every IC needs from its first turn, `MANAGER_ROLE` the Manager's part, which only a Manager is given, and what concerns a rarer event is said in the message that brings it (`review_request`, `stall_notice`, `approved_notice` with `WITH_SUB_TEAMS`, the hand-over brief, `manager_check`). Put new guidance in the message of the event it is for, not in the protocol. The shim needs the server's own address: `director_server_url`, or else the address the server is bound to (`OH_INTERNAL_SERVER_URL`, which its entry point sets), never one a request names. Without bubblewrap nothing holds an ACP agent's process, so its IC always gets its own worktree and what it commits outside its directory is refused at merge-back; `SessionTeam.boundary_enforcement` says which holds per place (`sandbox`, `checks`, `merge`), and an ACP Manager is then held by its prompt alone. A proposed sub-team may run on another agent with `model` in its proposal (`propose_teams`) (`SplitChild.agent_profile`), a name from `DirectorSettings.allowed_profiles`; that team's IC is started from the stored profile with `TeamLauncher.start_from_profile` as a child of the IC above, its Manager derived from it as always. The director asks an ACP agent in one of two ways, since it has no model the server can call. A question that needs nothing of the agent's conversation (`TeamLauncher.summarize` and `ask`: a team's title and headline, where a request goes, reports rewritten shorter) is a side question: a new, empty session of the agent's own ACP process, without the director's tools, that is prompted once and closed (`ACPAgent.ask_aside`, `ConversationTeamLauncher._ask_aside`), so it can be asked before the agent's first turn and pays for none of its context. A question on top of the agent's conversation (`TeamLauncher.ask_agent`: what a team changed, why it stalls) forks its session, and Claude Code cannot fork a session that has had no turn. Both are recorded as the agent's use, what the side session reports it cost included, and one that does not answer within `_SIDE_QUESTION_TIMEOUT` is cancelled alone. The conversation of an agent of the org cannot be forked and starts no child over the API (`director_router.not_an_agent_of_the_org`, a dependency `api.py` gives every conversation route, which acts on the three it names): a copy or a child would act as that agent, in no team. An agent is never derived from a Division Lead IC (`TeamMemberStartService.started_ic`), and none is started in a team a step is replacing or removing (`TeamMemberStartService._start_new`). A session the human gave no name is called by the title a model makes of its request: with the top team for the org's first session (`_summarize` with `rename`), and by itself for a session opened at a team the org has, which keeps its own name (`TeamSummaryService.name_session`).

## Tools and effects

**A team's work is what the branch of its checkout holds.** Three things keep that true, and none of them reads how a git command was written. The agents' own `git` (`git_index.git_script`) looks, after any command, at where the checkout is: off its branch and not in a rebase or a bisect, it points the checkout back, puts back the files the command changed where the agent may write them, and fails the command. In a checkout the director made, the branch is the one in the agent's `Scope.branch`, so a checkout that something else left elsewhere is back with the next command. It never asks git to go back with a checkout: in a sandbox the files of other teams stay behind and git refuses to come over them. An agent can reach another git, so the director looks for itself (`Checkouts.astray`, in `environment/git/checkouts.py`): `submit_review` is refused, and an acceptance is held, when the checkout is off its branch or when what was accepted from a team sharing the checkout (`Review.commit`) is not in its history. Do not add a check of a command's arguments here.

**What is kept, and in what shape.** Each thing of several steps the director begins is a model in `director/intents.py`, one for each kind, kept by `RunState` and handed to its `_do_<kind>` handler, which reads it with `intent.of(<Model>)`. A step records what it found with `run.step_done(intent, step, field=...)`; a field the kind does not have is refused. Add a field to the model before a step records it, and give it a default: an intent begun before the change is read with it. Files carry a version and one of an unknown version is refused, never read as empty and saved over: `org.json` (`version`), `settings.json` and `director.json` (`schema_version`; a file without one is of version 1), the run state (`SCHEMA_VERSION`). What each member of a shipped team is told of the org is held against `tests/agent_server/director/prompt_baselines/`; change one on purpose with `UPDATE_DIRECTOR_PROMPT_BASELINES=1` and review the difference.

**How the server holds it.** The director is a field of the server's `ServerContext` (`director_service`), set in `create_app` and replaced with the rest of the context on `POST /api/init`; routes ask for it with `dependencies.get_director_service` (`get_optional_director_service` where a route works without one). The org tree is `DirectorService.org`: do not call it `store`, a name `scripts/check_async_store_access.py` keeps for the file stores that block. A server built into one binary starts the tools shim by running itself with `mcp_shim.SERVER_ARGUMENT` (`acp.tools_server`, `__main__.main`), and `agent-server.spec` bundles `director/orgs/**/*.yaml`.

Agents act on the org through the tools in `director/tools/`, which run in-process: a tool resolves its caller with `OrgStore.find_by_conversation`, `director/agent_actions.py` checks the caller's role and place, and anything that touches a conversation (starting agents, sending messages, saving the tree) is queued with `DirectorService.work_queue.enqueue(effect, lane)`. Effects of one lane run in order and lanes run side by side: a place's id for its starts and messages, `review:<id>` and `headline:<id>` for its model calls, `org` for saves. An effect that must follow another has to share its lane. Keep it that way: tools run on agent threads and must not wait on a conversation, and nothing may call back into the store from a store listener. A start the server refuses because it runs `max_concurrent_runs` conversations waits in `StartLineService.when_there_is_room` (the place shows `waiting_to_start`) until a conversation stops running.

## Agent types

A team's type is its template (`agent_types.TeamTemplate`): a YAML file that names the members of such a team and says what they are told. There are no kinds of org beside it: every org runs the same steps, and what differs between teams is their type.

**Members.** `agents` names the members of a team, under any names (`Member`): the director's `tools` each has, the `lead_tools` it has instead at a Division Lead place, whether it `writes` (works in the team's folder), what it is called in what the director writes (`title`; its name when left out), its `text`, and what it is told of its part in the org after the director's own words (`protocol`). Every type names its members itself: nothing in the code holds a roster, and the shipped types each spell out an `ic` and a `manager`. This is decided, so keep to it: there is no list of roles or duties in the code. What a member may do is its tools, and the director finds whom to turn to by tool: the reviewer of a team is the member of the team above that has `review_team`. Do not add a branch on a member's name; ask the `Team`.

**What a type is checked for** when it is read (`TeamTemplate._has_whom_the_director_turns_to`), so that the steps always find whom they need: exactly one member `writes` (the agents' git assumes one writer per folder); `submit_review`, `review_team`, `propose_teams` and `approve_teams` are each held by exactly one member, and `settle_teams` by exactly one among the `lead_tools`; every tool is one the director has. A file that fails is refused and logged; the other types still load.

**The `Team` view** (`director/team.py`, `TeamTypeService.team(place)`) is how the service reads a team: `writer` (the member a task, a message from above and a person's words go to), `reviewer` (has `review_team`; the teams below turn to it), `manager` (has `approve_teams`, or `settle_teams` where the team only reviews a session), `member_with(tool)`, `conversation(member)`, `above`, `below`. It keeps nothing: the place is the org store's, the members are the type's. `TeamMessagingService.tell(place, member, text)` is the one way a member is told and started; `tell_writer` and `tell_manager` find that member of the place and call it. An escalation goes to the member of the same name in the team above, and where that team has none, to its reviewer. The org store is given `type_of` when it is made, and reads from it who works in a team's folder (`OrgStore.writer_of`).

**Who may write to whom is not in a type.** It follows the edges of the tree: a team sends tasks and messages down and work and escalations up, and the members of one team write to each other. Which member may use an edge is which tools it has (`msg_team`, `msg_ic`, `msg_manager`), and the checks of the target in `agent_actions` (`_team_below`, the `parent_id` comparisons) are the edge. Every message between agents goes through `TeamMessagingService.send_msg`, whichever tool sent it.

**The rest of a type is text**: which documents the team keeps and what each holds for it (`documents`, by the document's name; nothing said of one takes what the document says of itself), what each of the director's tools means to it (`actions`, by the tool's name), how its work is written up and reviewed (`review.write_up`, `review.checklist`, `review.checklist_skill` for a public skill such as `codereview`), the agent profile of the server its teams run on when a proposal names none (`sas_profile`, a software-agent-sdk profile), and tools none of its members is offered (`omit_tools`). A type and a profile are apart, and this is decided: a type without `sas_profile` says nothing of what runs its teams, a profile knows nothing of types, and any profile can run any type. A type's profile need not be in `allowed_profiles`, which limits what an IC names in a proposal and not what whoever runs the server wrote into a type; it must exist on the server, and `propose_teams` refuses a team of a type whose profile does not (`OrgRunService.profile_exists`). The proposal's own `model` holds over the type's. The top team of an org runs on the conversation its first message starts, whatever its type names.

**A document is a YAML file of its own**, one for each under `director/orgs/documents` (`spec`, `contracts`, `report`), and an org adds its own in the folder `documents` beside `director.yaml`, where a file of the same name takes the place of a shipped one. The file holds data only (`documents/declared.py`): its `name`, its `description`, the name of its `tool` and of its `protocol`. A type that names a document there is none of is left out and logged. Where documents are kept is `DocumentStore` (`documents/store.py`): `read`, `write`, `remove`, `discard` and `drafts`, by `DocumentRef(folder, name)`. What a session writes is its own until its work is accepted. The store decides nothing of who may read or write, and imports nothing of tools, types or the tree; `test_director_layering.py` holds it to that. `SessionRecordService.draft`, `_undraft`, `read_file` and `drafts` go through it. What a document does as its team's work goes on is its protocol, a subclass of `DocumentProtocolBase` (`documents/protocol.py`) registered with `register_protocol` (`documents/registry.py`) under the name the document's YAML gives; a document that names none is a plain text on the base class, whose every method does nothing. A protocol is a few facts the director reads, and the director never looks at a document's name to decide what to do. The facts are class attributes: `waits_for_team_changes` (a session's text becomes the org's with its team changes and not with its code), `read_by_sub_teams` (a team also reads the one of the team above), `usable_in_hand_over` (its tool works in a hand-over conversation) and `stays_when_team_is_removed` (the one a removed team wrote stays in its folder as an old one for the next team; `SpecProtocol` sets it). The director's own code and messages name no document an org declares: `service/`, `prompts.py`, `models.py`, `context.py`, `agent_actions.py`, `intents.py` and `tools/catalog.py` hold neither `spec` nor `contracts`, and `test_director_layering.py` holds them to that. A message that has to name a team's documents is given them as data (`prompts.KeptDocuments`, from `TeamTypeService.kept_documents`), and a line that tells a member what to do with one document is that document's own, in the `rules` of its YAML. The one exception is the report: the record each member of a team keeps of what it learned is the director's own, as messages are, kept as the one log of the store (`REPORT` in `documents/store.py`), with its own file, shortening and API fields. It is not made general, and a team whose type keeps none is never told to `report`. Two more facts say what the director does as the team changes: `needed_before_sub_teams` (the team's writer is refused a proposal of sub-teams while the document is empty; `ContractsProtocol` sets it, and `TeamDocuments.before_sub_teams_are_proposed` words the refusal with the document's name and tool) and `stays_when_team_is_removed` again (a document that does not stay goes out of the removed team's folder and into its record, `TeamDocuments.when_team_is_removed`; this holds for a plain document too, so no team finds a removed team's document as its own). **A protocol has no steps the director calls**: there were two, each used by one document and each a yes or no, so they are facts now. Add a fact, not a method, when a document differs by a yes or no; add a method only when a document must compute something the director cannot. A protocol acts only through the `DocumentStore` it is given and imports nothing of the director outside `documents/`. `ContractsProtocol` (`orgs/documents/contracts.py`) holds everything that is particular to contracts: add a rule about contracts there, not in `service/`. **Who reads a document** is said in two places, neither of them the director's own code. A document's protocol names the teams whose document of its kind a team reads (`read_from`: its own by default; `ContractsProtocol` adds the team above), and the kind of org may refuse on top (`OrgBase.allows_read`, in `director/org.py`; `TopDownOrg` in `orgs/top_down.py`, which the software and research orgs are, lets a team read only what it or a team above it keeps). Both are asked each time through the `TeamTree` (`documents/tree.py`: `above`, `below`) and nothing is kept, so a team that is moved under another reads that team's contracts with no step in between. `TeamDocuments.shown` is the one place that asks them. Do not work out who reads a document from the tree anywhere else. The service's org is `OrgSettingsService.org_kind`, the default one (`orgs.DEFAULT_ORG`) until an org can name its kind.

**What a type cannot do.** It cannot move a gate, change when a review is released or what counts as a stall, let two members write in one folder, or give a tool the director does not have; `read_team_context`, `raise_escalation` and `submit_review` are taken from nobody by `omit_tools` (`_TOOLS_NO_TYPE_REMOVES`). Folders, review and landing are the same for every team. **Naming the members.** What the director writes to agents names the members as the reader's own type does (`TeamTemplate.names`, a `Names` of the writer, the reviewer and the manager; `Team.names`, `TeamTypeService.names_at`). The builders in `prompts.py` and the answers in `agent_actions.py` take `names`; the director's fixed texts (the role texts, `WITH_SUB_TEAMS`, `STALL_QUESTION`) name a member by a field, `{writer}`, `{reviewer}`, `{manager}`, `{above_reviewer}` and the others of `Names.words()`, and `prompts.in_words` fills them in; it is only for text that holds nothing an agent or a person wrote. `prompts.org_protocol` builds the protocol from the type's members: how many there are and what each does, and one "If you are the …" part for the member that works and one for the member that reviews, which are one part where they are one member. What several of a member are called is the member's `plural` in the type's file. Which role text a member gets is decided by its tools, not its name (`prompts.role_text`): `MANAGER_ROLE` goes to the member with `approve_teams`, the Division Lead texts to the ones with `review_team` and `settle_teams` there, and a member with none of these is told its tools. Do not write "IC" or "Manager" into a new f-string; use `names`. The team above is named by its own type (`Names.above_writer`, `Names.above_reviewer`, set by `Team.names`). Limits of what is there now: the members of the teams below are named in the reader's own type's words, since their types are not known when the reader is briefed; the tool names `msg_ic` and `msg_manager`, the tool descriptions, the step names a person reads after a restart (`recovery.STEP_NAMES`) and the words of the event record (`prompts._EVENT_WORDS`) do not change with the type; and every member that does not work in the folder is derived from the one that does, so a type cannot say what a single member runs on. A file that says anything a type may not is refused when it is read (`extra="forbid"`, tool names checked against `DIRECTOR_TOOL_NAMES`).

The shipped types are those of the orgs under `director/orgs`: `orgs/software/types` (`software-engineer`) and `orgs/research/types` (`researcher`; `research-engineer`). An org is a subclass of `OrgBase` (`director/org.py`) that names its `types_folder`; a team of any org may be of any shipped type. The setting `org_kind` names the kind an org is of by the class's `name` (`software`, `research`, `open`; `orgs.ORG_KINDS`), and `OrgSettingsService.org_kind` is asked before anything goes between teams: `allows_msg` by `send_msg` (every message between agents), `allows_ref` by `send_ref` (a document passed once to another team for the session, kept as the run-state mark `SENT` and told in the context as `documents_passed_to_you`; the tool is `send_document`, which no shipped type gives), `allows_read` for what a document's protocol would show. `OrgBase` refuses nothing; `TopDownOrg`, which the software and research orgs are, passes and shows documents down the tree only; `OpenOrg` is `OrgBase` under a name. The others are the YAML files in the folder `types` beside `director.yaml`; one of the same name takes the place of a shipped one. Every type has a `description`, which is what an IC and a person choose it by; a file without one is refused. The files are read again whenever one is added, removed or changed (`TeamTypeService.agent_types`), so a new type can be given to the next team without a restart.

A team's type is `OrgNodeInput.agent_type`. It is named when the team is made: per sub-team in `propose_teams` (`ProposedTeam.type`), and for the top team of a new org in `CreateOrgRequest.agent_type` or with the first message (`RouteMessageRequest.agent_type`). A team whose making names none gets the default type (`OrgSettingsService.default_type`), never the type of the team above. Which types a new team may be and which is the default are set in two places, and this is decided: `DirectorSettings.default_agent_type` and `allowed_agent_types` hold for every org of the server (`director.yaml`), and an org sets its own over them in `OrgSettings`, kept in `settings.json` beside `org.json` in `refs/agents/org`, so the org carries them and another org on the same server has its own (`GET` and `PATCH /org/settings`). Both hold only for teams made from now on. A team that exists keeps its type whatever is allowed later, and `TeamTypeService.type_of` still gives it; a team whose type's file is gone is told as the default type is. A type that is not found or not allowed is refused where the team is made.

Nothing of the org is in an agent's system prompt, and this is decided: an agent of an org is a plain agent in an ordinary conversation, and everything it knows of the org it was told in that conversation. Its first message (`prompts.brief`, `TeamMemberStartService.briefing`) carries how the org works and what its part is (`prompts.role_text`: `ORG_PROTOCOL`, and `MANAGER_ROLE`, a Division Lead text or `HAND_OVER_ROLE` where they apply) and then what its type says to that member, as one `<TEAM_TYPE>` block before its task (`TeamTemplate.text_for`). `read_team_context` gives both again (`how_the_org_works`, `what_your_teams_type_says`). A first message can be summarised away when a conversation's history is shortened to fit its model, so the director says both again with the next message it sends after each shortening (`TeamLauncher.condensed`, the run-state mark `CONDENSED`, `MessageDeliveryService._condensed_since_told`, `context.again_block`), together with the team's whole context, since updates sent meanwhile may be gone too. An ACP agent keeps its own history and gives no such sign; it is not told again. Do not pass text to a launcher to append to a system prompt: an agent derived from another inherits that agent's system prompt, so whatever is put there follows every agent derived from it, of whatever team and type. What the person who opens a session appends is theirs and is passed through. `ORG_PROTOCOL` and `MANAGER_ROLE` hold the protocol alone and name no kind of work. The review request carries the checklist of the reviewed team's type (`TeamTypeService.review_instructions`), and the write-up question is that type's (`bugbot.write_up_question`).

## The org's own settings file

`Config.director_config_path` names the org's `director.yaml`: the fields of `DirectorSettings` as a person writes them (`org_config.load_org_config`). It is read when the server starts, and a file that sets something that is no setting, or to a value it cannot have, stops the server (`InvalidOrgConfig`). What is changed through the settings route afterwards is kept in `director.json` under `settings_changed` and holds over the file field by field, so a later edit of the file still changes every field nobody changed through the route. Without a `director.yaml` the settings are the ones last saved, as before. `director.json` stays the server's own state and is not for a person to edit.

## Settings and limits

`DirectorSettings` (`max_teams` for a team with every team below it, `max_depth`; `GET`/`PATCH /api/director/settings`, kept in `director.json`) are read by `split.check_limits`, when sub-teams are proposed, when they are approved and again when they are set up, so a lowered limit refuses the next sub-teams and removes nothing; `SessionMergeService._check_placement` holds a team a Division Lead Manager moves to `max_depth` as well. A session is counted where it is in the org: levels from the org's top team, and teams for the proposing place, every place above it in the session and every org team above the one the session was opened at.

## Status

A place's status is worked out, never declared (`org_store.status_of`); a tree team has none. It is `blocked` while the place is stopped, an escalation its IC raised is unsettled or an agent failed, else `working` while an agent runs (which follows the conversations through `ConversationService.add_execution_status_listener`), else `done` once it has submitted its work and that was not sent back (any review state but `changes_requested`), else `idle` (`blocked` if an agent is lost). An agent that is `blocked` or `lost` carries why in `AgentRef.reason` (`TeamLauncher.failure` reads the conversation's last `ConversationErrorEvent`; a start that failed keeps its error), and it is told, never only shown: `TeamMessagingService.tell_of_failure` records the event `failed` and calls `TeamMessagingService.tell_above`, which tells the IC of the team above, or, where no IC works above (the team a session was opened at, and its Division Lead place), raises an escalation that waits on the human (`failure_waits(role)`; `STALL_WAITS` for a team without progress). The human's answer goes to that agent and runs it again, or starts the team again when the agent is lost; a lost Manager is started afresh instead, with the answer, as it is by the next message sent to it (`TeamMessagingService.tell_manager`); the escalation is settled by itself once the agent runs (`OrgRunService._runs_again`). A step of the director that raises is kept as a `failed` event too (`TeamHistoryService.keep_failure`). Use `tell_above` for anything else that is wrong with a team and that somebody must hear of. The store recomputes it in `set_agent`, `set_review` and whenever escalations change; set a review with `OrgStore.set_review`, not `update_place`, or the status goes stale. `session_state._kept` leaves the running state out of what is kept of a place; it is read back from the conversations on load.

## Boundaries

A team is held to its boundary in code, not by its prompt. What one agent may write is a `Scope` (`director/scope.py`): a plain value of its checkout, its folder, its globs, the folders closed to it and the merges being finished. A merge that does not go through by itself is laid out in a folder of the reviewer that finishes it (`AgentConfinementService.merges_for`, `Scope.merge_root`), and the sandbox opens that folder to the reviewer's shell whether or not it writes anywhere else: the member that reviews need not be the one that works, and at a Division Lead place no member works. The folder is made when the shell is written, since the mounts of an agent's process are fixed when it starts. What the reviewer may change there is checked when the merge is committed (`merge_checkout.finish`). The org decides it in one place, `AgentConfinementService.scope_of(place, member, hand_over)`, and `Confinement` (`director/environment/git/confinement.py`) holds the agent to it: it writes the shell, the agent's `git` and the launcher of an ACP agent (`confine`), and checks file tools (`check`, which answers with a `Denied` that `boundary.worded` puts into words). Neither knows of teams or members, so `Confinement` is tested with a bare `Scope` (`test_director_confinement.py`); keep org logic out of both. `AgentConfinementService.guard_action` is asked before every action of every agent through `ConversationService.add_action_guard` and blocks a file tool (`director/scope.py` lists them and the field that names the file) from writing outside the team's directory, into a sub-team's directory, or anything at all for a Manager; a new file-writing tool must be added to that list. Where bubblewrap works, `director/sandbox.py` also writes one shell script per agent into `<git dir>/director-shells/` and the agent's terminal is started with it (`tool_params` on `start_conversation`/`start_child_conversation`), so the shell's mount namespace has the org's checkouts read-only except the team's own directory and the git directory; `OrgSummary.boundary_enforcement` says which of the two holds. Inside the git directory the director's own files (`director/`, `director-shells/`) and the hooks git runs for everyone (`hooks`) stay read-only, and so do git's `config` and what says where a checkout's git directory is (a worktree's `.git` file, and `worktrees/` but for the shell's own worktree, whose `commondir` and `gitdir` stay read-only too): the director's own git reads them outside the sandbox, where a filter, a merge driver or `core.worktree` an agent set would run its code or turn the director's git on the human's checkout. An agent sets what it needs for one command with `git -c`. A `commondir` git did not write (in the repository's git directory, or one in a worktree's that does not point two levels up) is refused by the director's git rather than followed (`git._planted_common_dir`), and `worktrees/` is made before a shell starts so that worktrees made later are closed to it. The hooks git runs, wherever `core.hooksPath` puts them, are read-only in every shell, and the hooks and director folders are made before a shell is written, so that none is left for an agent to make. The key file is masked after every other mount, so a team whose folder holds it cannot read it. The director's own git also runs no hook, no fsmonitor command and no signing program (`git._OWN_CONFIG`), so the repository's commit hooks do not run on the director's commits. `director.json`, which holds the key of the tool tokens, cannot be read from a shell, is written in place so that this holds for a shell that is already running, and is refused to a file tool that reads or writes it (`guard_action`), as is a write into a git directory that lies outside its checkout. A team's folder that is reached through a link opens nothing: the shell does not start. A guard that raises blocks the action (`EventService._guard_action`); an action nobody checked does not run. The agent's `git` (`director/environment/git/git_index.py`) follows a leading `-C`, refuses to run on an index it could not bring up to date, and undoes a commit that changes a file outside the team's folder (`commit`, `cherry-pick`, `revert`, `am`), refuses a `reset` that would take away commits of other teams before it runs, undoes a `merge`, `pull` or `rebase` that brought in changes outside the team's folder (without a sandbox nothing else stops one); what the boundary's `readonly` globs name, or its `writable` globs leave out (all of it when there are none), counts as outside the folder there and in `merge_back`, as it does for the file tools, and takes what was hidden from it as `HEAD` has it when a folder comes back to the team, keeping what it staged in its own, in a shared checkout and in a team's own worktree alike. It also puts a checkout back on its branch when `checkout` or `switch` left it (a branch the command made is deleted, one that was there stays): what is accepted is what the checkout's `HEAD` holds, and in a shared checkout that branch is every team's. A change by hand (`changes.write_by_hand`) takes the same lock and brings the agents' indexes up to date (`merge_back.bring_up_to_date`), and does not write through a link. The script is read when a shell starts, so a split narrows an IC's shell only from its next start. A sub-team's directory is closed to the IC above from the moment the team starts (`SessionTeam.agents` is not empty), not from the split: until then the IC may finish what it has there, though its `git` commits nothing in it, and `approved_notice` tells it how the split changed its work and which files it left uncommitted in each new directory (`_split_effects`). What it leaves is the team's: `TeamMemberStartService.do_start_team` names the files in the team's briefing (`left_for_team`) and `_pass_down` (same service) moves them into the team's own checkout when it has one (`git.bring_over`, kept at `refs/agents/left/<team>`); `submit_review` refuses the IC above while files in a sub-team's directory are uncommitted. A shell that was running before the team started is not narrowed, so what an IC writes from it into a started team's directory is taken out of its checkout when that team's work is accepted (`ReviewService._put_aside`, kept at `refs/agents/aside/<team>/<time>`) and the IC is told.

## The human's messages

`POST /api/director/org/messages` is the human's way in: it opens a session for the message at the nearest team above a directory (`boundary.nearest_team`), or with `session_id` says it in that session, and, without an org, takes up the one saved in the repository of the `conversation` it comes with or starts one there from the message. A client can therefore offer every new conversation's first message to it. Conversations the director starts itself (every agent but an IC that runs as the conversation a request came with) carry the tag `startedby=director` (`launch.STARTED_BY_DIRECTOR`), which clients use to keep them out of the list of the human's own conversations.

## Requests that go straight to a team

A message sent with `auto` (`RouteMessageRequest.auto`) may go to a team below the one its directory gives, without the ICs between taking a turn. What is decided here; keep to it. The rule behind all of it: a wrong team beside the right one costs more than a team too high, so every doubt moves the choice up and never sideways, and since nobody confirms the choice, an unsure one leaves the request where it was made. `director/routing.py` is pure and decides (`choose`); `service/request_routing_service.py` gathers what it decides from (`RequestRoutingService.choose_team`). Two things say which teams a request concerns: the tracked files and directories its text names (`paths_named`; a bare word that is a directory's name does not count), and a model that is shown a card of each team (inside a session, of each started one) and is asked twice with the teams of each level in the opposite order. The choice is the lowest team that holds every team named (`lowest_holding`), moved up, inside a session, to the first place that can take a request (`takes_requests`: started, not stopped, its IC not lost, its work not waiting for review, since such a team would go on changing what is being reviewed). It is sure only when both answers give the same team, every named path's owner is at or below it, and the team whose card clearly shares most words with the request (`best_by_words`) is on one line with it; named paths alone are sure when the model gives no usable answer. Agreement is the measure: never use a confidence the model states of itself. A request that names a file of a team outside the team it was made at goes no lower than that team, whatever the model answers: it is for a team above both. An answer that names an unknown team is no answer. A card (`Card`) holds only what the director holds of a team (title, directory, the task the IC above gave, the names at the top of its directory, the last requests it took), never its spec or reports, so no team can write itself into more requests. A request that went straight to a team is kept with its session until the session's work is accepted (`TeamHistoryService.keep_routed`) and then for the org in `.routed.json` of team memory (the last 200) and as an `asked` event in the record of the team above; every IC above the team has it in its context as `asked_directly_of_teams_below` (told with the next message, waking nobody, and only what is new of it: `context._LATEST`), and the review request quotes what was asked since the team's work was last accepted (`TeamContextService.asked_of`, by the order of the record, not by time, which is kept to the second). A team whose IC says the request is not its own calls `raise_escalation` with the category `misrouted`: that is no escalation and blocks nobody; `SessionLifecycleService.not_ours` hands the request to the IC of the team above, keeps a `misrouted` event, and the last ten are shown to the model. `DirectorSettings.route_requests` turns all of it off. Do not add a way to send to a team the director chose without the checks above, and do not route what is written to one agent or one team on purpose.

One team's IC never asks another's directly. What it needs of a team that is not above it is an escalation like any other: it goes to the IC above, which owns the contracts between its teams and has `msg_team`.

## Sessions

**Only sessions have agents.** A team of the org tree (`OrgNode` in `OrgStore._nodes`, `OrgStore.teams`, `org.json`) is the reference a new agent is briefed from: directory, boundary, spec, contracts, records, sub-teams. It has no agents, status, review, escalations or pending split, and `tell_writer`/`tell_manager` do nothing at a tree id. All work is done in sessions (`service/session_lifecycle_service.py`); the first request to an org opens the first one at the top team (`create_org` returns `OpenedSession`), and every later request opens another (`POST /api/director/org/sessions`, `route_message`).

- **Places.** A session has a place (`SessionTeam`, `OrgStore._places`, id `<team id>@<session id>`) at the team it was opened at and at each team below, each with its own agents, status, review, escalations and pending split. `OrgStore.get` returns a tree team or a place, `team` only the first and `place` only the second; the tree is read with `teams`, `sub_teams`, `teams_above` and changed with `update_team`, `move`, the places with `places`, `below`, `above`, `instance` and `update_place`, `move_place`. `org_store.team_id_of`/`git_store.team_key` give the team a place is of, which is what records are keyed by. A plain team id an agent names in a tool resolves to the place of its own session (`agent_actions._team_named`).
- **Division Lead place.** Nobody stands above a session's opening place, so the session has one more place at the team above (the top team itself for a session opened there): `division_lead_id`, `division_lead`, `parent_id` None, the repository checkout, nothing writable. The opening place's `parent_id` is the Division Lead place, so the review code needs no special case. Its IC is started on demand, only by `tell_writer(..., division_lead=True)` from `ReviewService.release_held`, as the Division Lead IC (its member's `lead_tools`, `DIVISION_LEAD_IC_ROLE`): it reads, reports and uses `review_team`. Places below the opening place are reviewed by the session's IC one level up, which gave the task.
- **Where a session is kept.** In the machine's run state only (`run_state.SESSION`, `session_state.py`), never in `org.json` or the team memory, so it is not exchanged with other machines: `org_persistence.reference` saves a tree team with its own fields only, and `session_state._kept` saves a place with its session. Its conversations stay, so a session resumes.
- **Checkout.** The opening place always works in a git worktree of its own (the given conversation with `worktree=True`, a derived IC from the repository's HEAD via `base=`); places below follow their team's isolation.
- **Routing.** A request written to a named team opens the session there; one written to the org as a whole is routed by `choose_team` (`auto`). What is typed in a session's conversation goes to that conversation.
- **Accepts in order, reconciled.** `ReviewService.check_accept` refuses an accept while work submitted earlier at the same place waits (`Review.seq`, a counter from `RunState.count`, not a timestamp), and asks the reviewer to reconcile (`reconciled`) when what the session did meets what was accepted meanwhile: files (`ReviewService._to_reconcile`), documents that land with its work (`TeamDocuments.changed_elsewhere`) or one it wrote for a team the org lost, of the kind that stays (`SessionRecordService.documents_inherited`). What the reviewer says holds only for what it was shown: `ReviewService._to_reconcile` returns a mark of what it compared, kept as the run-state mark `SHOWN`, and an answer given when the mark has changed shows the reviewer the new state instead (`_not_reconciled`). A session is never made to catch up while it works.
- **One lane for what the org shares.** Everything that writes the repository checkout for a session, `refs/agents/org` or `refs/agents/memory` runs in the lane `BASE_LANE`, one thing at a time in the order it was asked for: the accept of an opening place's work (`accept` with the payload flag `base`, `state.lane_for`), `ReviewService.pass_up` of one (`work_queue.run_in(BASE_LANE, ...)`), `land_org`, closing a session's waiting work, taking in a pulled org, `_name_org`, and rewriting the org's reports shorter. There is no landing lock. `SessionMergeService._weighing` only guards reading and changing a merge record; agent threads write nothing shared.
- **A change after an accept is said once.** A session whose work is accepted and that then sets up, replaces, moves or prunes a team, or writes a file of team memory, has changed what only another accept gives the org. `TeamHistoryService.note_change` remembers the session (`TeamHistoryService.changed_since_accept`), and when it is next at rest (no place working, no hand-over under way) `OrgRunService._remind_to_submit` tells its IC to submit again (`prompts.changed_since_accept`), once until the next accept. Commits of code alone are not noticed.
- **A session's own records.** Everything a session changes of team memory is its own until its work is accepted, kept in the run state with what it was written over: files (`FILES`: `spec.md` and `contracts.md` by session and path, text and base; `SessionRecordService.drafts`, `_draft`, `read_file`), reports (`REPORTS`, each with an id) and the records of teams it removed (`FORMER`). `TeamDocuments.shown`, `reports_of` and `former_teams_of` show a session its own over the org's. Contracts of a split, what `hand_over` passes on, and `_archive` all write there, never to team memory.
- **A file that cannot be written.** `OrgSaveService.commit_landing` returns the files of team memory that changed while a landing was made. They stay the session's drafts and the Division Lead IC is told (`prompts.files_not_written`); the next submit shows it both texts.
- **What lands on accept, in two parts.** The code part (code, the documents that land with it, and the reports, events and routed requests of teams the org has) lands on the Division Lead IC's accept. The org part (teams, team fields, the documents whose protocol sets `waits_for_team_changes`, and the records of teams the session set up) lands when the Division Lead Manager has settled what waits of it and every session that submitted earlier has landed its own (`SessionMergeService._in_order`, `SessionMergeService.org_turn`). Later work's code is never held up by an earlier Manager; its teams, and what waits with them, are. When the org part has nothing open and is first in order, both land in one step (`SessionMergeService.land_accepted` → `_land(top, seen, org)`): `OrgSaveService.commit_landing(tree=True)` stages a commit for team memory and one for the tree (`GitStore.stage`) and moves both refs in one `git update-ref --stdin` transaction (`git_store.swap_together`). Otherwise the code part lands with `waits`/`held` naming what stays the session's, `Merge.code_landed` is set, and the rest follows as the intent `land_org` (`SessionMergeService.do_land_org`), replayed after a restart. Each file is settled three ways (base, the session's, the org's now): written where the base still stands, nothing to do where the org has the same, and otherwise a conflict. A report, an event and a routed request are added once, by id. Other sessions read what landed in their next context update; nobody is woken. A landing holds `OrgSaveService.lock` from its first change of the tree to its commit (`_land`), so a save of the tree that falls in between waits and the tree never moves without team memory.
- **Team identity.** `OrgNodeInput.since` is when a team was set up. An id comes from the directory, so two teams can have one id; they are the same team only with the same `since` (`OrgStore.is_orgs`). A place whose team the org does not have, or has another team in place of, is not the org's team: it does not read that team's reports, and nothing it wrote lands on that team.
- **Nothing a session wrote is dropped on accept.** What it wrote for a team that is not the org's (reports, spec, contracts) is kept as that team's record: a `FormerTeam` with `ended="not_taken"` under the nearest team of the org that holds its directory (`split.home_of_lost`), with a `not_taken` event in that team's record.
- **Shape.** Split, replace and prune work on a session's own places, approved by the place's Manager as before; `SessionInput.shape` is the tree shape the session started from. The tree's shape changes only through `SessionMergeService._land` (`SessionMergeService._put_team`).
- **Without review.** An opening place that changed nothing itself and meets nothing accepted meanwhile goes up without the reviewer (`ReviewService.pass_up`, `Review.passed_up`); its review is `accepted` like any other.
- **What the human says in a session** is chosen among the session's own places (`choose_team(within=…)`), the teams it set up itself included. What the human asks anew is chosen among the tree's teams only.
- **Routing by where the human writes.** A new request (`route_message` with `auto`, `open_session` without a team) is chosen among the tree's teams. With `RouteMessageRequest.session_id` it continues that session: `_say_in_session` chooses among the session's places (`choose_team(within=…)`) and opens no session.
- **A request that is not a team's own** (`not_ours`) goes to the IC above inside a session. From the place a session was opened at, the session itself goes one team up the org (`SessionLifecycleService._lift`, `OrgStore.lift_session`): the team above becomes the place it is opened at, in the same checkout, the old one a sub-team of it, and the Division Lead place moves up. The human is asked only from the top team, or when the session's work is in review already.
- **Two gates, one record.** `SessionTeam.merge` on the Division Lead place (`Merge`, made when the work is submitted, `SessionMergeService.open_merge`) lists what waits as `MergeItem`s by `gate`: `ic` for code and specs, which the Division Lead IC settles with `review_team` before the merge, and `manager` for teams and contracts, which the Division Lead Manager settles with `settle_teams`. The two decide side by side and neither waits for the other. `Merge.seq` is its place in the order, `org_queued` says its teams and contracts wait behind an earlier session's (they are not worked out until it is first), `code_landed` that its code is in.
- **A reviewer that has to wait is told its turn.** Work is accepted in the order it was submitted, across sessions (`ReviewService._before`). A reviewer refused because another session's reviewer has not decided yet gets the run-state mark `TURN` and is told once that work is decided on or its session closed (`ReviewService.tell_turns`); it never has to ask again by itself.
- **Division Leads.** The two agents of a session's Division Lead place are the Division Lead IC and the Division Lead Manager (`SessionTeam.division_lead`, `is_division_lead`, `division_lead_id`, place ids ending in `@lead`, conversation titles). "Review" stays the word for the act, and "reviewer" for whichever IC reviews, an inner one included.
- **Spec and contracts say different things.** A spec covers only the inside of one team's folder; what teams promise each other is written only in contracts, and a spec does not repeat it (`ORG_PROTOCOL`, `WriteSpecTool`). So a spec lands with the code (Division Lead IC) and contracts with the teams they are true for (Division Lead Manager), and neither lead needs the other. The review request for a session's work shows what the session wrote of the documents that wait with its teams (`SessionMergeService.documents_waiting`), which its code is written to. Where the Manager does not take them (`Landed.others`), the session's IC is told the text that holds and to follow up on its merged code (`prompts.teams_settled`), and a `not_taken` event is landed for the folder's team (`_land_event`), also on close.
- **Work that is sent back joins the end of the line.** `SessionMergeService.sent_back` drops the merge record and a resubmit gets a new number; holding a place for work that is being redone would block every session behind it. What the Division Lead Manager had decided is kept in the run-state mark `DECIDED` and seeds the next record (`SessionMergeService.open_merge`), so it holds for whatever is unchanged (`_same`) and the Manager is not asked twice.
- **What waits for the Manager.** `SessionMergeService._manager_items` works it out from the org as it is now, never from what was kept: `split.merge_shapes(base, theirs, now)` with base `SessionInput.shape` (a team the session left alone stays as the org has it, one only the session changed becomes the org's, one both changed or that would not hang together is an item), and contracts drafts the org changed meanwhile. A decision (`use`, `replacement`, `under`, `named`) is carried over for as long as what it was made of is unchanged (`_same`). A team is compared by the team above it, its directory, its name, what it may write and read, its agent profile and `since` (`split.made_of`). After the org part lands the base is the session's own shape, so a team the org keeps otherwise is not brought up again.
- **Who settles what waits.** The Manager of the Division Lead place is asked when the work is submitted and it is first in order, only if something conflicts, once for each state of it (`SessionMergeService._ask_manager`, `Merge.asked`; `tell_manager(division_lead=True)`, `DIVISION_LEAD_MANAGER_ROLE`, `prompts.merge_request`). `settle_teams(teams, note, merge_choices)` only records: per team the org's or the session's (`TeamChoice`; a team taken from the session may be put under another team of the org, `under`, or called otherwise, `title`, checked by `_check_placement`: directory inside the other's and in none of its sub-teams', depth limit), per contracts the org's, the session's (the default) or a text (`DocumentChoice`). If what waits changed since the Manager was shown it, nothing is settled and it is shown again. Nothing is written until the code is accepted and it is its turn. A Manager that does not answer is asked again after `soft_check_in_minutes` and, once the code is merged, the human gets the escalation `ORG_WAITS` after as long again (`SessionMergeService.check_managers`, from `OrgWatchService.check_stalls`); answering it lands the org part with the org's standing wherever nothing was decided.
- **A team the org lost is never put back.** A session is not dropped when the tree no longer has a team of it. If the session changed nothing there the team stays gone. A team it set up under a lost one waits like any conflict, with `MergeItem.moved_to`: taken, it goes under the nearest team that holds its directory (or where the Manager puts it), that team's sub-teams inside its directory go under it, a `moved` event is kept, and the contracts the lost team set for it wait with it (a contracts item with `with_team`) to be added to the contracts of the team it goes under. A spec the session wrote for a lost team is shown to the Division Lead IC with the spec of the team that holds the directory now; unless the reviewer rewrites that spec in the same landing, the spec stays in its directory as an old spec of that team (`OrgNode.leftover_documents`), which the next session there is told to rewrite.
- **Closing.** Only the human closes a session; one whose work was accepted stays open so more can be asked in it. On close, a merge record whose code is in lands its org part with the org's standing wherever nothing was decided (`SessionMergeService.settle_on_close`, in the base lane): what the session wrote lands where the org has the team and is a `not_taken` record where it has not. A record whose code was never accepted is dropped, and what the session wrote goes with it (`SessionRecordService.leave`), named in the `session_closed` event, which is kept only if the org knows the session.
- **The reviewer merges.** Work whose files do not merge with the checkout above is not sent back. `ReviewService._finish_merge` lays the merge out (`Checkouts.lay_out_merge`, which is `merge_checkout.prepare`: a detached worktree in `director-merging/` of the git directory, conflict markers left in; run-state mark `MERGING`) and tells the reviewer (`prompts.merge_prepared`). The reviewer edits only the listed files and runs no git there: `guard_action` refuses any other file, and on the next accept `Checkouts.finish_merge` (`merge_checkout.finish`) refuses a changed file that merged by itself or a marker left in, stages the listed files, commits, and `Checkouts.take_merge` (`merge_back.take_merge`) fast-forwards the checkout above. It holds for inner places too. The team is told which files its reviewer finished. Files outside the team's directory still go back. Sending the work back or closing the session takes the laid-out merge away.
- **The reviewer writes specs.** `review_team(specs=[DocumentChoice])`, for a session's work only: per directory of the work (or of a team that inherits a lost team's spec) the org's stays, the session's holds, or the reviewer's own text does (`SessionMergeService.document_choices`, applied to the session's drafts by `_take_spec_choices` right before they land).
- **Events, threads and routed requests are a session's own** until its work is accepted (`EVENTS`, `THREADS`, `ROUTED` marks, read and written only by `SessionDraftService`; `TeamHistoryService.record_event`, `keep_routed`, `session_drafts.keep_message`). Events and routed requests land with their team's part; threads never land, they reach the org only inside a removed team's record. Readers (`history_of`, `routed_requests`, `org_history`) show the org's plus the open sessions' own, the latter marked `TeamEvent.unaccepted`.
- **What is saved and exchanged.** What a session has is written to the run state as soon as it changes (`_keep_sessions`), not with the tree's delayed save. A fetch takes only `refs/agents/org` and `refs/agents/memory` (`org_sync.fetch`), a push gives only those; what a server keeps under `refs/agents` for itself is never exchanged. The lane orders one server; two servers on one repository are held apart only by the compare-and-swap underneath.

## Sessions an event opens

A session need not be opened by the human. `POST /api/director/org/events` (`SessionLifecycleService.open_from_event`) opens one for something that happened outside: a ticket that was filed, an alert, a schedule that came due. The director knows nothing of where events come from. An automation of the OpenHands automation service receives the event (a webhook source with its signature check, or a cron trigger), runs `director/automations/open_session/main.py` (standard library only, uploaded as a script automation; its docstring says what to set), and that posts the text, the event as it was received and what names it. To support a new kind of event, register its source in the automation service and write the templates; add nothing here.

The team is chosen as for a message the human sends with `auto` (`_team_for`, shared with `route_message`: `RequestRoutingService.choose_team` at or below the team `path` gives), and the session is opened with the same `open_session`, so its cost limit, its review and its merge are a session's. What differs is that nobody is there: an event is refused where a human would be asked (`Unavailable` with no org or a paused one, `Conflict` at `max_open_sessions`), for the automation's run to fail and be sent again; an event that names itself (`source.event_key`, kept as the `TRIGGERED` marks, the last `_EVENT_KEYS_KEPT`) opens one session however often it is delivered, also after that session closed; and its IC is told so in the request itself (`prompts.event_request`, with the payload shortened to `EVENT_PAYLOAD_SHOWN`), not in the protocol.

Who asked is the session's `source` (`RequestSource`: `human` by default, `automation` with its name, ids and event key), kept with the session and on a request that was routed. A session whose source is not the human is closed once all of its work is the org's (`SessionMergeService._close_unattended`, after `_after_landing`, with the same `CloseSession` step the human's close begins; not while what it makes of the org's teams waits to be settled), since left open it counts against `max_open_sessions` and nobody would close it. The org keeps such sessions open with `close_unattended_sessions: false` in its own settings (`OrgSettings`, `PATCH /api/director/org/settings`). An escalation of such a session waits for a human as any does.

## Conversations the human reads

Every agent's conversation is an ordinary conversation of the server; one the director started itself is tagged `startedby=director` (`launch.STARTED_BY_DIRECTOR`), which a client leaves out of its list of chats. An agent derived from another does not take over that conversation's `humanjoined` tag, and never waits for an action to be confirmed (`NeverConfirm`), whatever the conversation it comes from does: nobody is there to confirm, and the guard and the sandbox are what hold it. One the human writes in also gets `humanjoined=true` (`launch.HUMAN_JOINED`, `MessageDeliveryService.joined`, the run-state mark `JOINED`), and is then listed with the human's own: `tell_writer(human=True)` does it for a message sent through the director and for the request a session is opened with, and a client that writes into an agent's conversation directly calls `POST /api/director/org/conversations/{id}/joined`. A session's conversations are titled with the session (`API · Refunds (IC)`). `GET /api/director/org/conversations/{id}` (`TeamContextService.place_of`) says where a conversation is (team, role, session) and links to the conversations one level away: the agents of the place above (for a session's opening place, its Division Leads), the other agent of its team, and the ICs of the places directly below (for a reviewer, the session's IC). A client uses the links to open one conversation inside another.

## Titles and headlines

Team titles and `headline`s come from one separate model call per team (`director/headline.py`, through `TeamLauncher.summarize`), never from the agents' own conversations, and a failed or slow call leaves the name the team has.

## Pruning

A Manager removes a team directly below its own with `prune_team`: `TeamSplitService.do_prune` stops and deletes the conversations of the team and of every team below it, discards the uncommitted changes in the team's directory after saving them as a commit under `refs/agents/pruned/<team id>/<time>` (`git.save_and_discard`), and removes the place, so the directory is the IC's above again; that IC is told the Manager's reason. A prune never starts a team, and it waits until no agent of the team or of a team below it is in a turn (`MessageDeliveryService.wait_until_quiet`).

## The agents' git

Every IC's terminal is started through a script in `<git dir>/director-shells/`, confined or not, because that script also puts the `git` from `director/environment/git/git_index.py` first on `PATH` (through a bash `--rcfile`, since `~/.bashrc` may reorder `PATH`). Inside the org's repository that `git` runs the real one on `<git dir>/agent-index-<conversation id>`, where everything outside the team's directory is reset to `HEAD`, marked skip-worktree and ignored, so `git add -A` and `git commit -a` take only the team's own files; it resyncs when `HEAD` or the team's sub-teams change, runs HEAD-moving commands one at a time under `flock`, and after a commit resets the committed paths in the checkout's own index. Do not give agents a bare `GIT_INDEX_FILE`: an index that is one commit behind reverts that commit when it is committed from.

## Specs, contracts and ownership

A team is told its own boundary's `spec.md` and two sets of contracts, nothing else of the teams above: the spec, the `contracts.md` of its own boundary (between its sub-teams) and the `contracts.md` of the boundary of the team above (between it and the teams beside it), each as its session has it (`TeamDocuments.shown`, by what each document's protocol says of who reads it). The contracts of an approved split are written to `contracts.md`, not into the spec, so whatever a sub-team must respect has to be in them. `GET /api/director/org/nodes/{id}/ownership` (`director/environment/git/ownership.py`) lists the files of a place's checkout by the direct report that owns them and the files that conflict when the tips of the checkouts of the place and its reports are merged in memory with `git merge-tree --write-tree`; uncommitted changes are not compared. For a tree team it lists the files of the repository's checkout by the sub-team that owns them and looks for no collisions (`collisions_checked` is false).

## Changing team memory in place

**A document says what its team is told of it.** `rules` in its YAML are lines added for the teams whose type keeps it: `everyone`, `writer` and `reviewer` to `<ORG_PROTOCOL>`, and `manager`, `lead_reviewer`, `lead_manager` and `hand_over` to the `<ORG_ROLE>` of that role (`prompts.role_block`), `teams_replaced` to the writer once sub-teams it had were replaced (`approved_notice`, `replaced_job`), `sub_teams_changed` to the writer once sub-teams were set up below it or one was pruned (`approved_notice`, `pruned_notice`, `replaced_job`, `pruned_job`, and `handed_over_notice` for a document the hand-over conversation did not write), and `handed_over` to the writer of a team that is handed what the teams before it left (`TeamTypeService.document_rules`, `prompts.org_protocol`); no text in `prompts.py` names a document.

**A document says its own part of a briefing.** `DocumentProtocolBase.told_in_briefing` returns the parts (a heading and a text) an agent's first message gives of it: a plain document its team's own, the contracts the two kinds a team reads, the report its entries. `TeamDocuments.briefed` asks each and adds, after a document's parts, what teams before left of it in the folder (`prompts.left_document`). `prompts.brief` and `hand_over_brief` take those parts and name no document.

**What the documents are to a team is worked out by `TeamDocuments` (`documents/team_documents.py`), not by the service.** It takes the store of documents, the protocols the org declared and the kind of org, and each of its functions takes a `Reader`: a team as plain values (its `TeamRef`, the documents its type keeps, what teams before it left, what its members are called). `TeamTypeService.reader_of` is the one place that makes a `Reader` of a team of the service, and the service calls `self.team_documents.<function>(self.reader_of(team))`. It knows nothing of `DirectorService`, the tree's store or run state, so it is tested with a store that keeps texts in a dict (`tests/agent_server/director/test_team_documents.py`). What stays in the service is what is about sessions and run marks: which teams a session removed (`SessionRecordService.documents_inherited`, `_documents_left_in`), what was passed or handed over (`documents_passed_to`, `session_drafts.handed_over_to`), and the report. Put new logic over documents in `TeamDocuments`; do not give it the service. **A document brings its own tool; the director has none for any one document.** The tool's name (`tool`, or `write_<name>`) and what agents are told of it (`tool_description`) are in the document's YAML; what it takes and what a call does are its writer's (`DocumentWriterBase.arguments_for` and `__call__`, in `documents/writer.py`), which its protocol names as `writer_class`. **A document is three small parts, as a tool of the agent SDK is a definition and an executor**: the YAML is the data, the protocol (`documents/protocol.py`) says what the document is (the facts, who reads it, what they are told of it), and the writer carries out a call of its tool; `EditorWriter` is the plain one and the default. What passes between them is in `documents/schema.py` (`DocumentToolCall`, `DocumentToolResult`, `ShownDocument`, `DocumentsBriefed`), and the registry of protocols and of declared documents in `documents/registry.py`. Keep it so: do not put writing back on the protocol, and do not add a third class per document. With no protocol named, a document is a text its team rewrites with the commands of the file editor, so a new plain document is one YAML file in the org's `documents` folder and a line in the types that keep it. The pieces, each of which knows only the one before it: `TeamTypeService._declared` reads the documents and calls `declare`; `tools/documents.py` makes a `ToolSpec` of a document; `tools/definition.py` listens (`when_declared`) and makes and registers the tool of the agent SDK (`tool_of`), once for a name; `agent_actions.write_document` checks that the caller's type gives it the tool and hands the call to the protocol's writer (`protocol.writer(call)`). Do not add a tool for a document to `tools/catalog.py`, and do not branch on a document's name in `write_document`: what is particular goes in the document's protocol or writer (`orgs/documents/spec.py`, `contracts.py`). **A document is written with its own tool alone.** `propose_teams`, `review_team`, `hand_over` and `settle_teams` take no document and are the same for every org, whatever documents it keeps; do not add an argument for a document to `tools/catalog.py`, and do not change a tool's action class when a document is declared (the classes are the whole server's). An IC writes the contracts with `write_contracts` before it proposes sub-teams: the proposal is refused while they are empty (`ContractsProtocol.needed_before_sub_teams`, `TeamDocuments.before_sub_teams_are_proposed`; a team whose type keeps no contracts, or an org whose `contracts` names no protocol, is never refused). The proposal's message shows its Manager the documents the sub-teams will read (`TeamDocuments.read_by_sub_teams`, the ones whose protocol is `read_by_sub_teams`); a reviewer adds what accepted work establishes with the same tool after `review_team`. `hand_over(team, text)` writes no document: the text is kept for the team in the run-state mark `HANDED` (`SessionRecordService.removed_team_handed_over`), told to its writer as `handed_over_to_your_team` in its context (so with its next message, or in its briefing), and the team writes what should last itself, as the `handed_over` rule of each of its documents says. **Which of two versions of a document holds is the merge's to ask, not the document's**: `merge_choices` on `review_team` and `settle_teams` is a list of `DocumentChoice(document, folder, use, replacement)` (`use` is `org`, `session` or `replacement`; a team's choice and a kept merge item say `use` too), declared in the catalog. `review_team` takes the documents that land with the work and `settle_teams` the ones whose protocol sets `waits_for_team_changes` (`SessionMergeService.document_choices` refuses the other kind); a reviewer's choices are kept with the acceptance by document and folder. The catalog has no tool for any document: `report` too is made of `report.yaml` and `ReportProtocol`. **What an agent's context says of a document is the document's to say too** (`DocumentProtocolBase.told_to_reader`): the plain answer is the team's own text under the document's name, so a plain document is in the briefing, in `read_team_context` and in the context updates with no more code; `ContractsProtocol` gives the two lists the contracts are told as. `TeamDocuments.told` puts them into `context_of`, for the documents a team's type keeps and any other the team is shown one of. `ReportProtocol` (`orgs/documents/report.py`) is a log: its writer (`ReportWriter`) adds an entry (`DocumentStore.append`), its part of the context is the entries (`DocumentStore.entries`). The store keeps one log, the report's (`TeamHistoryService.entries` and `append`, which the store of documents is given as its `Logs`); where its entries are kept, how they are merged and how they are rewritten shorter is still the director's (`git_store`, `TeamSummaryService.compact`). A team is told its reports only if its type lists `report` among its `documents`. **The API gives a team's documents as one list** (`NodeMemory.documents`, of `TeamDocument`; `TeamDocuments.listed`): each with its name, what it holds for the team's type, the folder of the team that keeps it, and whether it is the team's own, one a team above keeps for it, or one a team before it left. There is no field for any one document; Canvas renders the list. A test that calls a shipped document's tool takes it from `tests/agent_server/director/document_tools.py`.

A spec and the contracts are kept outside the working tree, so an agent's file editor cannot reach them. The two tools that change them therefore take that editor's own commands and arguments, and this is decided: write and edit are one tool, as in the editor, not two. `write_spec` and `write_contracts` take `create` (the whole text in `file_text`), `str_replace` or `insert`. The change is made by the editor itself on a copy of the text (`memory_edit.edited`, `openhands.tools.file_editor.editor.FileEditor`), so its rules and its refusals are the editor's: the text to replace must be there exactly once. One thing is added to it: `insert` with no `insert_line` adds at the end. The contracts of a directory are its team's IC's: it writes them before it proposes sub-teams, and the Division Lead IC is refused. What accepted work establishes reaches every sub-team when the reviewer adds it with `write_contracts` after `review_team`. None of this asks the Manager, which reads the contracts with a proposal and in its context. Reports stay as they are: only ever appended.

## Review

Work a team's IC submits with `submit_review` (refused while anything in its directory is uncommitted, or while its work already waits) ends that IC's turn and is reviewed by the IC of the team above, not by a separate agent and not by a Manager: `DirectorService._request_review` first asks the team's own IC, on top of its conversation with `TeamLauncher.ask_agent`, which records nothing in it, to write up what the team changed since `SessionTeam.base_commit` as a pull request description. No diff is sent to a model; the question carries only git's list of changed files. The account is stored on `SessionTeam.review` and sent to the IC above in a review request, together with OpenHands' public `/codereview` skill as the instructions that IC applies (`director/bugbot.py`; `find_review_instructions` is injected so tests never load public skills). A request goes to the reviewing IC as soon as its team has submitted, and this is decided: no team's review waits for the teams beside it (`DirectorService._release_reviews`; the run-state mark `HELD` only says a request is not yet delivered, which a paused org makes up for on resume). The IC may end its turn without deciding, to compare the work with what a team beside it will submit; the next request names what still waits for it (`prompts.still_undecided`), and whether to wait is for its team's type to say. What must be whole is checked where work goes up instead: `submit_review` is refused while a sub-team of the caller that has agents and is not `blocked` is working, waits for the caller's review, or was sent back and has not submitted again (`agent_actions.submit_review`). That holds at every level, so nothing unfinished reaches the Division Lead IC or the main checkout, and landing needs no check of its own. A sub-team that neither submits nor blocks therefore holds back the reviews of the teams beside it until it is told to the IC above as stalled or is stopped (below). That IC decides with `review_team`. An accept merges the tip of a team with its own worktree into the checkout above (`director/environment/git/merge_back.py`, under the lock the agents' `git` takes) and tells nobody further up unless the IC passed `needed_above`; work that conflicts or reaches outside the team's directory is sent back instead. A session's work goes into the human's own checkout only while that is on the branch the session was opened on (`SessionInput.branch`); on another branch, or with uncommitted work in the way, the human is asked with the escalation `MERGE_WAITS` (`ReviewService.ask_to_clear`) and their answer merges it. There is no limit on rejections; `Review.round` counts them, and every `manager_check_ic_setbacks` of them on one piece of work wake the Manager above (`request_changes`), as that many escalations do. Each change is reviewed once, by the IC directly above the team that made it: after an accept, `DirectorService._pass_up` looks at the team above, and when all its sub-teams are accepted and it changed nothing itself (`_own_changes`: nothing committed since its `base_commit` or uncommitted in its directory outside its sub-teams') its work is merged into the checkout above and marked `accepted` with no review (`Review.passed_up`), and so on up. A team that did change something, and a session's opening place whose work meets what was accepted meanwhile, is left for its IC to `submit_review`; a merge that fails on the way up stops there and tells that team's IC. `DirectorService.settled()` waits for effects that effects queue, so a test can assert right after it.

## Memory sync and reports

The team memory leaves the machine only with the org, when it is pulled or pushed (`OrgSyncService._pull_memory`, below); there is no sync of team memory alone. `GitStore.merge` settles what both sides changed itself: reports become the union, and of any other file the local text is kept and named in `kept_local`. Either agent of a team records decisions, setbacks and reflections with `report`; they are kept in the team's folder of team memory beside its other documents, in `<folder>/report.json` for all its members (`git_store.reports_file`; each report names the member that wrote it), are only ever appended, and are read by the two agents of that team alone (`TeamHistoryService.reports_of`), in `read_team_context` and in a briefing. Nothing is inherited down the tree and the human has no route to add one. When a report takes an agent's past `DirectorSettings.report_compaction_chars` characters (and a quarter of that is new since the last rewrite), a model rewrites them into one report marked `compacted` (`director/compaction.py`); the size is counted in characters because an external agent has no tokenizer at hand.

## Resting an IC

`submit_review` rests the IC: `DirectorService._rest` pauses its conversation after the step it is in (`TeamLauncher.pause`) and, in the lane of the team's messages, waits until it has stopped, so that nothing sent to it afterwards lies unread; the next message runs it again. An IC that runs its own tools is not paused, since that would end its process: the tool's answer tells it to end its turn, and one that still runs after `_REST_CHECKS` is cut short with `TeamLauncher.stop` (ACP `session/cancel`), which costs it the step it is in. Standing guidance from the human is a convention, not a feature: it goes into the repository's `AGENTS.md`, which every agent reads.

## Messages and proposals

An IC and a Manager talk in free text: `msg_manager` (an IC to its own Manager) and `msg_ic` (a Manager to its own IC, or with `team` to the IC of a team directly below). `TeamMessagingService.send_msg` keeps each message in the run-state mark `THREADS`, named `.threads/<manager place>/<ic place>.json` (`records.thread_name`), and delivers it through the outbox; the threads are the session's own and never land in team memory, except in the record of a team that is removed; `GET /api/director/org/nodes/{id}/messages` returns the threads a place's agents take part in (`threads_of`). An IC proposes sub-teams with `propose_teams` (`teams` with `name`, `path`, `instruction` and optional `reason`, `model`, `writable`, `readonly`, `isolation`, plus `contracts`, `keep` and `text`); the tool's schema refuses what is not a proposal, and the Manager reads the proposal as a message of the thread (`split.as_written`). A team without sub-teams has no use for `msg_manager` and is refused it. A proposal that fails any check (`split.normalize_split`, `check_limits`, the allowed profiles) is refused to the IC and nothing reaches the Manager; one that passes is kept in `SessionTeam.pending_split`. The Manager sets the teams up exactly as written with `approve_teams`; a `msg_ic` to its own IC while a proposal waits decides nothing (both are told it still waits), and a later proposal replaces an earlier one. There is no count of attempts. An IC never configures a Manager: every team gets one, derived from its IC.

## Replacing teams

Proposed teams may overlap the ones the team already has: a team whose directory equals, holds or lies inside an existing direct sub-team's replaces that sub-team (`SplitProposal.replaces`), and whatever the new teams leave of the directory is the proposing IC's again. An IC that already has sub-teams must say what becomes of each: the proposal's `keep` lists, by name or team id, every sub-team that stays as it is (`SplitProposal.keeps`), and `split.normalize_split` refuses a block that leaves a sub-team neither kept nor replaced, keeps one it also replaces, or names one the team does not have. Only a proposal's first check asks for `keep`; the checks at approval and at set-up pass none. A proposal never removes a team without replacing it: that is the Manager's `prune_team`. A replaced team's own sub-teams stay and are moved with `OrgStore.move_place` (which re-routes their escalations) under the new team that holds their directory, else under the proposer; a proposed team may not sit inside such a sub-team, and a team with a worktree of its own cannot be replaced while sub-teams work in that worktree. `TeamSplitService.do_split` fixes the whole plan in the intent's first step, waits until the replaced teams and their sub-teams are at rest (messages to them stay in the outbox meanwhile), merges what replaced teams committed in their own worktrees into the proposer's checkout (`_take_in`; a conflict declines the approval and changes nothing), saves their uncommitted work under `refs/agents/pruned/`, removes them and sets the new teams up.

## Starting teams

Setting teams up starts nothing: a new team has no agents (`SessionTeam.agents` is empty) and its `instruction` is kept as what it is for (the run-state mark `TASK`). Its IC is added and started by the first thing sent to it (`TeamMessagingService.tell_writer`: a `msg_team` from the IC above, a message from the human, a review request for a sub-team moved under it), with that message as the end of its briefing; send to an IC through `tell_writer`, never by looking its conversation up. A team that was never started owes nothing: it cannot stall, holds back no review of its siblings and does not keep the team above from going up (`OrgWatchService.may_stall`, `ReviewService.release_held`, `ReviewService.pass_up`). An agent is derived from the nearest IC at or above its team that has started (`TeamMemberStartService.started_ic`). Teams waited for are kept in memory only (`MessageDeliveryService._settling`) and found again when the step is carried out again. A Manager is woken by its briefing, a `msg_manager`, an escalation from below, a team its IC stopped and the two checks below; nothing wakes it when a sub-team is `blocked` or when approved teams cannot be set up: its look says how long a blocked team's IC has waited, and a set-up the runtime refused is kept in the record as `declined` (`_decline`), where it reads it.

## What a removed team leaves

A team that is removed, by a proposal that replaces it or by `prune_team`, leaves nothing a later team finds by accident (`TeamSplitService._archive`, called before `store.remove`): it makes one record (`FormerTeam`: title, directory, purpose, how it ended, its review, its reports in full and as one report a model shortened, what each of its documents kept of itself by name (`documents`: the contracts between its sub-teams, for one), its message threads), takes its threads out of the session's run state (`session_drafts.take_threads`) and drafts the removal of its `contracts.md`; the run-state marks `TASK`, `PROGRESS`, `CHECKS` and `REPORTS` of its place are cleared. The record is the session's own (`FORMER`) until its work is accepted; then it is written to `.former/<team id>/<time>.json`, and the team's reports and record of its sub-teams are deleted in the same commit if the org no longer has that team (`Landing.forget`). If the org kept the team, the record lands as `not_taken`. This matters because a team id comes from the directory, so a new team in the same directory has the old team's id; until the accept, `OrgStore.is_orgs` keeps the new team from reading the old team's reports. Recording a removal again changes nothing, which is what makes the step safe to carry out twice. Only a document whose protocol sets `stays_when_team_is_removed` stays where it is (`spec.md`, in the shipped orgs): a new team is marked with the ones it finds in its directory, each by name (`OrgNode.leftover_documents`, set in `TeamDocuments.left_in` for a team's own directory and for the directories of replaced teams that hold it or lie in it; after a prune, on the team above), `TeamDocuments.left_to` returns them with who left each, briefings and the context (`documents_left_by_teams_before_you`) say they are old, and writing its own with the document's tool clears the mark. Reports belong to a member of a team, not to a conversation: `<folder>/report.json` Sub-teams of a replaced team that was stopped go on under the team they are moved to (`TeamMessagingService.go_on(own_too=True)`), with their time without progress started again.

## Managers and their looks

A started team has its IC alone. Its Manager is added to `SessionTeam.agents` and started by the first thing sent to it (`TeamMessagingService.tell_manager`: a `msg_manager` or an escalation a Manager below raised), briefed with the team's task from the run-state mark `TASK`, so send to a Manager only through `tell_manager`. The director also wakes a Manager to look at its teams on two counts kept apart in the run-state mark `CHECKS` (`TeamMessagingService.count_accepted_review`, `count_escalation_from_below`): every `DirectorSettings.manager_check_accepted_reviews` (default 5) reviews its IC accepted with `review_team` (work that went up by itself in `ReviewService.pass_up` is not counted), and every `manager_check_ic_setbacks` (default 3) escalations that the IC of one team directly below raised or passed up to its IC on the work that team has in hand. Each count starts again when it wakes the Manager and neither touches the other; a team's escalation count also starts again when its work is accepted (`_work_accepted`), since what it does next is other work, so the count belongs to a team and a piece of work, not to a team for good. 0 turns a check off. The wake-up (`prompts.manager_check`) lists the teams below with their status, review, escalations and time without progress, and asks for nothing.

## Stalls and stopping

What a session uses is counted, and its cost can be limited. With every look of the stall watch `OrgWatchService.count_use` reads what each conversation of a session has used (`TeamLauncher.usage`) and adds what is new since the last look to `SessionInput.usage` (the run-state mark `USE` keeps the last reading of each conversation, so a count that begins again with a server takes nothing away). A conversation's use is read per model it ran on (`launch._used`): an agent that runs its own model (an `ACPAgent`) reports its cost itself, and what it read from and wrote to its cache apart from its input, which is added to the input because it is nearly all of it; another agent's cost is what the SDK recorded with LiteLLM's prices and, where that is nothing (a model behind a gateway or under a name of its own), what `pricing.priced` derives from LiteLLM's public price list for the model its name ends in, cache reads and writes at their own price. Tokens no price is found for are counted in `Usage.unpriced_tokens` and are in no cost, so no limit holds them; the page says so. The director's own model calls on an agent's model are counted the same way and added. `DirectorSettings.session_cost_limit` (US dollars; 0: none) is what a session may cost; `SessionInput.cost_allowance` is where it is held next. A session that reaches it is put to rest the way a stopped team is (`Stopped` on the place it was opened at, so everything sent to its agents waits) and the human is asked with the escalation `LIMIT_WAITS`; their answer lets it go on for as much again (`OrgWatchService.go_on_past_limit`) and is sent to its IC. What a team uses stays no measure of the team: it limits a session and is told to no agent. `DirectorSettings.max_open_sessions` (0: no limit) refuses one session more in `open_session`. A team started from a profile spends under the caps of the agent it is started for (`max_iterations`, `max_budget_per_run`), as a derived agent does.

A team whose work was accepted and that is then written to by the IC above (`TeamMessagingService.send_msg`, `_assign`) owes a review again: its review is cleared, so what it does next is not taken up with a sibling's accept, and it counts as a team that may stall. Teams that get nowhere are found by time, not by counting rejections. Apart from that, the IC above is told how a team that owes work stands every `DirectorSettings.hard_check_in_minutes` (default 360, never less than `soft_check_in_minutes`), whether or not it shows progress (`prompts.check_in_notice`, in `OrgWatchService.check_stalls`): the mark's `checked` is when that IC last turned to the team (`progressed(..., by_above=True)`: its task, a `msg_team`, work sent back) or was last told of it, a stall notice included, so the two are never sent at once; a check-in also sets `told`, so a stall notice does not follow before `soft_check_in_minutes` more. Teams of one IC that are due at the same look go to it in one message. It goes only to a team with an IC above it, never to the human, and asks the team nothing. The director keeps when each team last got anywhere in the run-state mark `PROGRESS` (`OrgStateService.progressed`: its start, a `submit_review`, a review decision, an escalation raised or settled, an accept of one of its sub-teams, a `msg_team` to it; and a new commit under its directory, which `OrgWatchService.check_stalls` finds with `git.last_commit_in`). Every `STALL_POLL_SECONDS` `OrgWatchService.check_stalls` looks at each team that owes work nobody is waiting to give it (`_may_stall`: not submitted, or sent back; not `blocked`, not under a stopped team) and, after `DirectorSettings.soft_check_in_minutes` (default 120, 0 turns it off) without progress, tells the IC above once (the human, with the escalation `STALL_WAITS`, where no IC works above: `TeamMessagingService.tell_above`), and once more for each further such stretch: `prompts.stall_notice` carries how long, what the team's own IC answers when asked on top of its conversation (`STALL_QUESTION` through `ask_agent`; not asked while it is in a turn) and the git commands to look for itself, and the reviews held for that IC are released with it. The first notice about a team counts as progress of the team above, so that IC has one stretch to act before it is told on itself. The clocks start again when an org is resumed and when a server starts; the clock is injected (`clock`, `stall_poll`) and tests call `OrgWatchService.check_stalls` themselves. An IC writes to the IC of a team directly below with `msg_team` (`TeamMessagingService.send_msg`, kept with the session in the run-state mark `THREADS` and returned by `threads_of` as a `Thread` with `ic_to_ic`); nothing goes back up that way, the team answers through its work or an escalation. As a last resort an IC stops a team directly below with `stop_team`: `SessionTeam.stopped` (set with `OrgStore.set_stopped`, which makes the status `blocked`) records why and which conversations were in a turn, the agents of the team and of every team below it are paused, `MessageDeliveryService.deliver` holds everything sent to them in the outbox (the human's words too), and the Manager of the stopping IC's team is told. A stopped team goes on when that IC writes to it with `msg_team` (`TeamMessagingService.go_on` delivers what waited in the order it was sent and runs the agents that were cut off), can be replaced through a proposal (`propose_teams`) and can be pruned by the Manager like any other team; the human has no control to stop one.

## Context

An agent is told its team's context without asking. `TeamContextService.context_of` builds it (it is also what `read_team_context` returns), a briefing ends with the parts it does not already say in its own words (`context.briefing_block`), and what the agent was told is kept per conversation in the run-state mark `TOLD`. A change to the context never sends a message, since every message starts a turn: `MessageDeliveryService.deliver` compares the context with what was told (`_with_what_changed`) and appends a `[director] context update` block to whatever message goes to that agent next, the human's included. `context.steady` leaves out what comes and goes with every turn (`working`/`idle`, headlines), a list that only grew is told as what was added, the list of sub-teams is told as the teams that changed or went (`context._entries_changed`), a part that is no longer there is told as `null`, the same entries in another order are told as nothing, and an agent is not told back its own reports or the escalations it raised. An update stays small: it never carries what the agent wrote itself (`MessageDeliveryService.knows` takes its own `spec` and `pending_split` as told; an IC is not told its own `status`), the review entry is state and round only, a proposal is its status and team names outside `read_team_context`, lists known by an id (`context._KEYED`) are told as added, changed and removed, one text is cut at `context.CUT` characters, and a briefing leaves out empty fields. A system prompt cannot carry this: it is fixed when a conversation starts and derived agents inherit their parent's. Add a field to the context in `context_of` and it reaches briefings, updates and the tool alike. A model call the director makes for itself, apart from any conversation, goes through `TeamLauncher.ask` with its own `usage_id`.

## Unfinished work and recovery

The director's unfinished work is kept outside git history, in the SQLite file `<git common dir>/director/state.db` (`director/run_state.py`): which agents were running, which teams wait for a run slot and in what order, the multi-step actions it began (intents) and the messages it has not delivered. A multi-step action goes through `DirectorService.resumable_work.begin`, which records it before its first step; `ResumableWorkService.carry_out` runs the `_do_<kind>` handler, which marks each finished step with `run.step_done` and skips marked steps, so every handler must be safe to run again. Messages to agents go through `MessageDeliveryService.post`/`send` (held, then delivered: at least once). `POST /api/director/org/pause` and `/resume` stop and continue all of it, `GET /org/recovery` says what a resume will do; a server that starts with unfinished work loads the org paused (`shutdown` or `crash`) unless `DirectorSettings.resume_on_start` is set. `director/recovery.py` drops run state that no longer fits the sessions (another server's file, a step of a place that is gone or whose split or review no longer stands, a message to an agent that is gone) and names what it dropped. Finished intents and delivered messages are deleted, so the file holds only what is open. An agent a restart cut off is told to carry on (`TeamMessagingService.run_again`) and shows paused until it is seen running (`OrgStateService.resuming`): until then its conversation still says the error the restart left, which is not a failure of its own.

## Inheritance, hand-over and the record

What a team inherits from the teams before it is decided, so keep to it: nothing by itself. A team is cleared, split or merged only through a proposal (`propose_teams`) and removed through `prune_team`; there is no merge or re-parent command, and a clear is simply a different team proposed for the same directory. What the removed teams left is given to the IC that proposed the change, or to the IC above a prune, in hand-over mode: a side conversation of that IC which the director starts for that hand-over alone (`TeamSplitService.do_hand_over`; it is no agent of its own but `AgentRef.hand_over` on the team's IC, found by `OrgStore.find_hand_over`, derived from the IC's conversation and briefed by `prompts.hand_over_brief` with each team's reports as one report, in full, the contracts between its sub-teams, its spec, who has its directory now, and the team's own context). It shares nothing with the IC's main conversation, which is only told that it runs and, when it ends, what it did (`handed_over_notice`); its status does not count toward the team's, it edits no files, and of the director's tools only `read_team_context`, `hand_over` and `write_spec` work in it. Each hand-over gets a new one, which replaces the one before (a split finished again after a restart begins none while its hand-over is still open); where it cannot be started it is tried once more, and then the mode stays on the IC with the status `lost` and the IC's main conversation is told so and nothing more, by decision: the job is not moved there. A hand-over conversation is paused, run again and read back after a restart as an agent's own is (`recovery.put_aside_stale` keeps its marks, `_resync_hand_overs` ends one that finished or was lost meanwhile). That IC decides which team gets what with the `hand_over` tool (`DirectorService.hand_over`: notes are kept with the team's IC reports as a `Report` with `handed_over`, which a briefing and the context show as written by the IC above; contracts replace the team's own `contracts.md`; both are the session's own until its work is accepted). `hand_over` starts nothing, nothing waits on it, and it can be repeated; `read_team_context` returns the records again for an IC (`former_teams`, in full only from the tool; the context told with every message only names them). The hand-over conversation is told to rewrite the team's spec, and the answers of `approve_teams` and `prune_team` tell the Manager it may need to explain the change with `msg_ic`. The `contracts` of a proposal that replaces teams take the place of the team's `contracts.md`; a proposal that replaces none adds to it. What became of the teams directly below a team is kept in team memory as `TeamEvent`s (`.history/<team id>.json`, written when the session's work is accepted; until then `TeamHistoryService.record_event` keeps them with the session: set up, accepted, sent back, stalled, stopped, replaced, pruned, and each time the Manager was woken with the reason). It outlives the teams it is about; a team's own file goes with it when it is removed. Both agents read it through `read_team_context` (`track_record_of_the_teams_below`), a review request carries the team's record, and `manager_check` lists it, with the teams that are gone. It is not part of the context told with every message, so it adds no context update. A team that was set up and given no task for `soft_check_in_minutes` is told to the IC above once and not again, since a team may wait on purpose (`prompts.unstarted_notice`, from `OrgWatchService.check_stalls`); it is not a stall and is not recorded as one. The memory route returns the removed teams and the record for a client (`NodeMemory.former_teams`, `NodeMemory.history`). `GET /api/director/org/history` returns the records of all teams as one list, newest first (`TeamHistoryService.org_history`, without the `needed` events). How teams are split, merged and pruned is decided, so keep to it. An IC splits by concern first (one thing a team can own behind a short contract) and for efficiency; teams working at the same time follow from that and are not a reason to split (`ORG_PROTOCOL`). A proposed team and the block may carry an optional `reason` (`SplitChild.reason`, `SplitProposal.reason`). The director adds to a proposal, for the Manager, what it knows (`TeamContextService.facts_of_proposal`, `prompts.proposal_facts`): files in each directory, commits that changed two proposed directories together, and teams that had a directory before with why they were pruned. Proposals and approvals are kept in the record (`proposed`, `approved`). A Manager declines what its IC proposed with `decline_teams` and a reason (`agent_actions.decline_teams`), which is kept as `declined` with the proposal's directories (`TeamEvent.paths`) and told with a later proposal for the same directories; a message with `msg_ic` decides nothing, and what was proposed waits on the Manager until it approves or declines or the IC proposes again. A Manager is woken only by the two counts it had (accepted reviews, and one team's escalations on the work in hand); work that is sent back is recorded, and wakes the Manager once it was sent back as often as that number. When the escalation limit is reached the `woken` event names the team, and `track_records` counts for each team its tasks and the ones on which that limit was never reached; `manager_check` tells the Manager that as the team's success rate (`success_rate`, with `success_rate_meaning` naming the number from the one setting `manager_check_ic_setbacks`). Token use is deliberately not a measure of a team: tasks differ in difficulty. A Manager may prune any team directly below; the runtime refuses none on its record, by decision. It is told to prune only a grossly inefficient team, that it is never obliged to, and to wait until a team has had enough tasks to judge it by; how many is its judgment and deliberately no setting. What says that two teams should be one is counted, not guessed: a write by one team's IC that the runtime refused because the file is a sibling's (`guard_action`), and a review finding on one team's work that names a sibling's file (`request_changes`), are kept as `needed` events with the other team (`TeamHistoryService.record_need`, `TeamEvent.other_id`, the same file and way once, which is looked up in the record itself and so holds across restarts). `prompts.needs_between` counts them for each pair of teams that are there, from the time each was set up. From `NEEDED_WORTH_SAYING` (3, deliberately no setting) the IC is told in a review request for either team and by `read_team_context` (`teams_below_that_needed_each_other`); a Manager is told any count when a proposal replaces both teams. It wakes nobody, merges nothing, and is by decision not part of a Manager's look. Escalations that merely name another team are not counted: a text match can be wrong. The human still cannot prune, replace or split.

## Exchanging an org with a remote

An org is exchanged with a remote of its repository only when asked, as git does a branch: `POST /api/director/org/push` and `/org/pull` (`director/environment/git/org_sync.py`) move `refs/agents/org` and `refs/agents/memory`, nothing else: sessions, with their agents, checkouts and branches, stay on the machine that has them. A pull is a merge (`director/org_merge.py`, a pure function over saved teams): a team or a field changed on one side only is taken from that side; the same field changed on both, a team removed on one side and changed on the other, and a spec or contracts both rewrote in the same lines are conflicts. With conflicts nothing is written, the org stays paused, the merge is kept in the run state and `GET /org/merge`, `POST /org/merge/resolve` and `/org/merge/abort` settle it; finishing writes a commit with both parents. A saved team has only what `OrgNodeInput` has, so nothing of a machine's work is merged, and a pull leaves the open sessions as they are (`OrgSyncService._apply`). A clone that pulled an org has its teams and no agents: work begins there with a request, which opens a session. An agent of a session whose conversation is not on the server is `lost`, and `POST /org/sessions/{session id}/teams/{team id}/start_again` starts that place afresh in its own checkout. Without a conversation `start-again` starts the place's IC like the IC above it in the session, or failing that like the IC another session started with (or from the team's own agent profile). `tree-stream` carries `paused` and `merging` in its snapshot and an `org_state` event on every change. When teams change place (`OrgStore.move`, a tree read again, a pull) every subscriber is sent its snapshot anew (`OrgStore.show_again`) and starts over from it. The intents `accept` and `request_review` are forgotten only after the tree they changed is saved, so a server that ends in between does them again; an `accept` found already accepted still does what follows it (`ReviewService.pass_up`).

## The human's edits

The human reads and changes a team's files through `director/environment/git/changes.py`: `GET /api/director/org/nodes/{id}/changes` lists what differs in the team's directory from `SessionTeam.base_commit` (uncommitted and new files included), `.../changes/file?path=` gives both sides of one file, and `PUT .../files?path=` writes one file, commits it alone as `Edited by hand: <path>` and tells the team's IC, which starts a turn of it. The write is held to what the team's own agents may write (`changes.edit_refusal`, the same rules as `Scope.refuse`, worded for a person) and is refused with 409 while an agent of the team is running. All three take the id of a place; a tree team has no checkout and answers 404. There is no shell for the human.

What an accept took can be read after its session is closed: an `accepted` event keeps the two commits (`TeamEvent.base`, `head`) and the team's directory (`paths`), and `GET /api/director/org/accepted/changes?base=&head=&path=` and `.../changes/file` read them from the repository (`accepted_changes`, `accepted_file`). Only commit ids are passed to git. The commits are in the repository as long as the work was landed; a session closed before that can lose them, which is a 404.

## ACP processes

OpenHands starts an `ACPAgent`'s command in a process group of its own and ends the whole group when the agent is closed (the command is usually `npx`, which starts `node`, which starts the agent); the director adds nothing to that. The director's `sandbox.command_script` adds bubblewrap's `--die-with-parent` for an agent's whole process, not for a terminal's shell (`shell_script`): the kernel counts the thread that started a process as its parent. A message to an ACP agent in the middle of a turn ends that turn, so `MessageDeliveryService.deliver` leaves the director's own notices in the outbox while such an agent runs and `MessageDeliveryService.note_running` delivers them when its turn ends, joined into one message (`deliver_what_waited`), since each of several would end the turn the one before began; only what the human said (`route_message`, `answer_escalation`) is posted with `at_once=True`. The intent `finish_split` is saved before it is forgotten, like `accept`.
